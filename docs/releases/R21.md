# R21 — Numeric Source and Portable Representation

Status: **Complete — E21-1 through E21-5.** The skeptical release truth
audit (E21-5) verdict and evidence are recorded in
`docs/analysis/r21-release-truth-audit.md`. `GENIA_STATE.md` sections
9.21–9.22 remain final authority for implemented behavior; this document
summarizes it.

R21 follows completed R16 through R20. Its purpose is narrow: freeze how
numeric *source* is classified and how that classification is represented
in portable Core IR, before any later release changes runtime numeric
mathematics (R22), rendering/JSON interchange (R23), or brings up a second
host (R24). R21 implements **no** Decimal/Rational/Float64 runtime
arithmetic, no new numeric equality or map-key behavior, and no
rendering/formatting/JSON change.

The approved contract is
`docs/design/r21-numeric-source-portable-representation-contract.md`.

## Scope

R21 covers:

1. Classifying numeric source text as **Integer** (`DIGIT+`) or **Decimal**
   (dotted, exponent-only, or dotted-exponent forms) purely lexically.
2. Rejecting leading-dot (`.5`) and trailing-dot (`5.`) forms, and
   malformed exponents (`1e`, `1e+`), deterministically.
3. Canonical base-10 normalization for Decimal source (a coefficient and
   exponent such that value = coefficient × 10^exponent) that never
   constructs a host binary float during classification.
4. A canonical **tagged** `IrLiteral` payload for numeric source in the
   portable Core IR — `{"kind": "integer", "digits": "..."}` or
   `{"kind": "decimal", "coefficient": "...", "exponent": "..."}` — using
   the existing `IrLiteral` node family; no new numeric Core IR node.
5. Preserving existing unary-sign lowering (`-1.25` is unary minus over the
   positive literal) and ordinary slash/division lowering.
6. Shared, host-neutral `spec/parse/*` and `spec/ir/*` evidence, proven to
   agree between the in-process Python path and the R16 subprocess
   protocol adapter.

R21 explicitly does **not** include Decimal/Rational/Float64 runtime
values or arithmetic, cross-kind numeric equality/comparison changes,
map-key reconciliation for new runtime numeric kinds, canonical
Decimal/Rational/Float64 display, numeric format-spec behavior, JSON
numeric encode/decode behavior, or a C++ host implementation. Those belong
to R22, R23, and R24.

## Source classification

```text
integer          := DIGIT+
decimal-dotted    := DIGIT+ "." DIGIT+
exponent          := ("e" | "E") ("+" | "-")? DIGIT+
decimal-exp       := DIGIT+ exponent
decimal-dot-exp   := DIGIT+ "." DIGIT+ exponent
```

```genia
1        -- Integer source
1.0      -- Decimal source
1.25     -- Decimal source
1e3      -- Decimal source (1000.0)
1E+3     -- Decimal source (1000.0)
1.25e-2  -- Decimal source (0.0125)
```

`.5` and `5.` are not R21 numeric literals — both raise a deterministic
`SyntaxError` at parse time. `1e` and `1e+` (no digits after the exponent
marker) also raise a deterministic `SyntaxError` naming the malformed
exponent, rather than mis-tokenizing.

Equivalent Decimal spellings normalize to the same evaluated value while
remaining Decimal kind even when that value is mathematically integral:

```genia
1.0 == 1.00
-- true
100e-2 == 1
-- true
```

The source sign is not part of the numeric token — existing unary lowering
is unchanged: `-1.25` is unary minus applied to the positive Decimal
literal `1.25`, not a signed literal.

## Portable Core IR payload

Numeric source lowers through the existing `IrLiteral` Core IR node with a
canonical tagged payload instead of a bare host number:

```text
source: 42
IrLiteral.value = {"kind": "integer", "digits": "42"}

source: 1.25
IrLiteral.value = {"kind": "decimal", "coefficient": "125", "exponent": "-2"}
```

Every payload field is a string; no host-native binary float ever appears
in the portable payload, even for Decimal source. Huge Integers preserve
their exact digits (arbitrary precision, unaffected by this change). `/`
stays ordinary `IrBinary(op=SLASH)`; the frozen minimal portable Core IR
node family in `docs/architecture/core-ir-portability.md` is unchanged.

Numeric literals in **case-pattern position** (`IrPatLiteral`) are
intentionally unaffected by this release — only expression-position
`IrLiteral` carries the tagged payload, matching the approved contract's
scope.

## Evaluator compatibility

R21 does not change what a Genia program observes when it evaluates a
numeric literal. The reference host's evaluator unwraps the tagged payload
back into the exact same `int`/`float` value it produced before this
release; this is documented compatibility work, not new R22 runtime
semantics.

## Shared evidence

18 `spec/parse/*` and `spec/ir/*` cases cover Integer classification,
dotted/exponent-only/dotted-exponent Decimal classification, equivalent
Decimal spellings, huge Integers, malformed-exponent rejection,
leading/trailing-dot rejection, unary-negative lowering, and slash
lowering. `tests/spec/test_r21_conformance_protocol_evidence_855.py`
proves every one of them passes identically through both the in-process
Python path and the R16 generic subprocess protocol adapter — never
`unsupported`.
