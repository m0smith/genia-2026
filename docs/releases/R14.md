# R14 — Composable Lifecycles

Status: **Complete — E14-1 through E14-15 delivered.** `docs/design/r14-composable-lifecycle-contract.md`
is the approved E14-0 contract; this page documents the implemented E14-1
(parent/child instance/scope core), E14-2 (peer-attachment breadth over
that same core, with no runtime-code change), E14-3 (`lifecycle_repeat`
over eager List and lazy Flow sources), E14-4 (`lifecycle_config` provider
binding, also with no runtime-code change to the core), E14-5
(`http_operation`, the first R14-HTTP slice, with zero network IO and no
host capability), E14-6 (a narrow Python-host outbound HTTP transport
capability with no Genia-visible surface of its own), E14-7
(`web.http_send`, the first genuinely Genia-visible outbound-HTTP call),
E14-8 (comprehensive regression proof of the protected-HTTP-credential-sink
contract, zero runtime-code change), E14-9 (`@get`/`@post` declarative
annotations plus `web.send_annotated`, composing the unchanged E14-5/E14-7
surface), E14-10 (proof that an R8 request handler can create outbound
HTTP client lifecycle instances while the server stays active, zero
runtime-code change), E14-11 (proof that `lifecycle_scope`/
`lifecycle_repeat`/`lifecycle_context` already compose into a repeated
record-processing pipeline, zero runtime-code change), E14-12 (the
YouVersion Bible proxy proving application, composing R13 configuration,
R10 protected values, R8 server mode, and R14's outbound HTTP client
lifecycle in one real program, zero runtime-code change), E14-13
(the combined cross-cutting hardening gate over all of E14-1 through
E14-12 -- import/discovery inertness, serve-mode annotation
non-self-execution, sentinel-free rendering, a combined multi-peer
failure matrix, bounded Flow termination with no leak, Python-exception
normalization, combined server/request/outbound-client resilience, and
parse/Core IR regression, zero runtime-code change), E14-14 (documentation
and implemented-truth synchronization only, no runtime behavior), and
E14-15 (the release-wide skeptical truth audit, **PASS** verdict, and
distillation, no runtime behavior) slices.
`GENIA_STATE.md` remains authoritative for current behavior.

The delivered APIs remain **Experimental** and Python-reference-host-only;
shared/multi-host conformance remains Partial. R14 is release-complete;
see `docs/strategy/r14-composable-lifecycles.md`.

Run:

```bash
genia -c '
config = {name: quote(config), enter: (h) -> some("prod"), exit: (h, s) -> some("nil")}
result = lifecycle_scope([config], (root) ->
  lifecycle_child(root, [], (req) -> lifecycle_context(req, quote(config)) |> unwrap_or(none))
)
display(result)
'
```

Output:

```text
"{status: ok, state: completed, scope: root, phase: exit, peer: none(\"lifecycle-no-peer\"), result: some({status: ok, state: completed, scope: child, phase: exit, peer: none(\"lifecycle-no-peer\"), result: some(prod), primary_failure: none(\"lifecycle-no-failure\"), cleanup_failures: []}), primary_failure: none(\"lifecycle-no-failure\"), cleanup_failures: []}"
```

`lifecycle_scope(peers, work)` enters each peer in list order — here one
peer named `config`, whose `enter` exposes the string `"prod"` as context —
then runs `work` with a handle to that scope. From inside `work`,
`lifecycle_child(root, [], req_work)` runs a nested child scope: `req_work`
reads the parent's exposed context by name through
`lifecycle_context(req, quote(config))`, proving context flows inward across
a parent/child boundary without becoming a lexical binding. The child's own
`LifecycleResult` comes back as ordinary data nested inside the parent's
`result` field — it is never inspected or auto-propagated, matching "child
completion returns result/control to parent" and "child failure does not
implicitly terminate the parent."

A failing peer or a raising `work` callable normalizes into the closed
`LifecycleResult`'s `primary_failure` instead of raising past the call:

```bash
genia -c '
bad = {name: quote(bad), enter: (h) -> err("not-configured", {}), exit: (h, s) -> some("nil")}
display(lifecycle_scope([bad], (h) -> 1))
'
```

```text
"{status: error, state: failed, scope: root, phase: enter, peer: some(bad), result: none(\"lifecycle-no-result\"), primary_failure: {peer: some(bad), phase: enter, reason: not-configured, context: {}}, cleanup_failures: []}"
```

E14-1 adds exactly three ordinary calls — `lifecycle_scope`, `lifecycle_child`,
`lifecycle_context` — over the entry/work/unwind algorithm and scope lifetime
state machine locked by the E14-0 contract. It adds no `lifecycle_repeat`,
`lifecycle_config`, HTTP operation/client, new syntax, or parser/Core IR
change; see `GENIA_STATE.md` section 9.8 for the complete implemented
contract, including the partial-entry/failure matrix and non-shadowing rules.

E14-2 proves that the same `peers` list is not limited to one entry: any
number of independent lifecycle concerns can attach to one scope, entering
in list order with each earlier peer's exposed context readable by every
later peer's own `enter`:

```bash
genia -c '
peers = [
  {name: quote(config), enter: (h) -> some("prod"), exit: (h, s) -> some("nil")},
  {name: quote(metrics), enter: (h) -> some({calls: 0}), exit: (h, s) -> some("nil")},
  {name: quote(diagnostics), enter: (h) -> some({env: lifecycle_context(h, quote(config)) |> unwrap_or("unknown")}), exit: (h, s) -> some("nil")}
]
result = lifecycle_scope(peers, (root) -> lifecycle_context(root, quote(diagnostics)) |> unwrap_or(none))
display(result)
'
```

Output:

```text
"{status: ok, state: completed, scope: root, phase: exit, peer: none(\"lifecycle-no-peer\"), result: some({env: prod}), primary_failure: none(\"lifecycle-no-failure\"), cleanup_failures: []}"
```

Here `config`, `metrics`, and `diagnostics` are three independent peers
attached to one execution scope — none of them is the parent or child of
another. `diagnostics`'s own `enter` reads `config`'s already-exposed
context through `lifecycle_context`, proving a later peer sees an earlier
peer's exposed value while attachment stays a flat, ordered list rather than
a parent/child chain. E14-2 adds no new public function: this example, and
the deterministic three-peer enter/reverse-unwind order, partial-entry
failure matrix, and peer-isolation proofs, exercise the unmodified E14-1
algorithm at greater breadth — see `GENIA_STATE.md` section 9.9 for the
complete proven contract.

E14-3 adds `lifecycle_repeat(peers, source, element_work)`: the same
entry/work/unwind algorithm runs once per consumed element, with reserved
`quote(element)`/`quote(index)` context populated before any attached
peer's own `enter` runs:

```bash
genia -c '
peers = [
  {name: quote(record_context), enter: (h) -> some({row: unwrap_or(none, lifecycle_context(h, quote(element)))}), exit: (h, s) -> some("nil")},
  {name: quote(diagnostics), enter: (h) -> some("checked"), exit: (h, s) -> some("nil")}
]
work(h) = unwrap_or(0, lifecycle_context(h, quote(index)))
results = lifecycle_repeat(peers, ["alpha", "beta", "gamma"], work)
display(results |> map((r) -> [r.scope, r.status, r.result]))
'
```

Output:

```text
"[[element, ok, some(1)], [element, ok, some(2)], [element, ok, some(3)]]"
```

Each of the three list elements gets its own fresh element scope
(`scope: quote(element)`), with both `record_context` and `diagnostics`
entering and unwinding around it in the same deterministic order E14-2
already proved. `record_context`'s own `enter` reads the reserved
`quote(element)` context — populated before either peer entered — so it
never needs the caller to thread the row value through by hand.
`lifecycle_repeat` over a `Flow` instead of a `list` returns a lazy,
single-use `Flow<LifecycleResult>`: pulling one item pulls exactly one
element from the source, runs that element's scope fully to completion, and
yields its result — bounded early termination (`take`, a manual break)
never leaves a scope partially entered, because the yielded element's
cleanup already ran. E14-3 adds no new list/Flow mechanism: this reuses the
exact `close_on_early_termination`/generator-`close()` idiom `map`/
`filter`/`take` already use — see `GENIA_STATE.md` section 9.10 for the
complete implemented contract, including the reserved-name non-shadowing
rule and the eager/lazy dispatch rules.

E14-4 adds `lifecycle_config(provider)`: a pure factory that binds an
already-constructed configuration provider as one reserved peer, readable
by any descendant scope through the same `lifecycle_context` accessor
every other peer already uses:

```bash
genia -c '
provider = config_provider([{kind: quote(values), values: {APP_PORT: "9090"}}]) |> unwrap_or(none)
config_peer = lifecycle_config(provider)
result = lifecycle_scope([config_peer], (root) ->
  lifecycle_child(root, [], (req) -> {
    bound = unwrap_or(none, lifecycle_context(req, quote(config)))
    config_view(bound, "APP_")("PORT")
  })
)
display(result)
'
```

Output:

```text
"{status: ok, state: completed, scope: root, phase: exit, peer: none(\"lifecycle-no-peer\"), result: some({status: ok, state: completed, scope: child, phase: exit, peer: none(\"lifecycle-no-peer\"), result: some(some(9090)), primary_failure: none(\"lifecycle-no-failure\"), cleanup_failures: []}), primary_failure: none(\"lifecycle-no-failure\"), cleanup_failures: []}"
```

`lifecycle_config(provider)` performs no lookup or acquisition itself — it
only captures the already-constructed `provider` from `config_provider` and
exposes it as ordinary lifecycle context under the reserved name `config`.
The child scope's own `work` reads that exact provider through
`lifecycle_context(req, quote(config))`, then constructs an ordinary
`config_view` from it exactly as if the provider had been threaded through
by hand — R13's `config_get`/`config_view`/`secret_view` Outcomes, protected
carriers, and declassification rules are entirely unchanged. E14-4 adds no
new algorithm or accessor: attaching a second `lifecycle_config` peer
anywhere in the same root/child/element ancestry chain is rejected by the
same non-shadowing check E14-1 already enforces for any other peer name —
see `GENIA_STATE.md` section 9.11 for the complete implemented contract.

E14-5 adds `http_operation(method, base_url, path, headers, query, body)`:
one inert, closed `HttpOperation` value with **zero network IO** — the
first R14-HTTP ticket, and the first to add no host capability at all:

```bash
genia -c '
op = http_operation(quote(post), "https://api.example.com", "/v1/items", {}, {}, {kind: quote(json), value: {name: "widget", count: 3}})
display(op)
'
```

Output:

```text
"some({method: post, base_url: https://api.example.com, path: /v1/items, headers: {content-type: application/json}, query: {}, body: {kind: json, value: {name: widget, count: 3}}})"
```

`http_operation` validates all six fields — `method`, `base_url`, `path`,
`headers`, `query`, `body` — in that order, before constructing anything;
the first invalid field short-circuits with
`err("http-operation-invalid", {stage: quote(<field>)})`. Here every field
is valid, so the call succeeds: the `{kind: quote(json), value: {...}}`
body is passed through the existing `json_encode` capability purely to
fail fast (a `json_encode` failure — including one caused by a protected
value inside `value` — would surface as this same `body`-stage `err`), and
because `headers` didn't already set `content-type`, `http_operation`
injects `application/json` — an explicit `content-type` header, had one
been supplied, would have been left untouched. Constructing, `display`-ing,
or otherwise inspecting an `HttpOperation` never performs network IO; a
protected value placed in `headers` (never `query`, which rejects
protected values outright) stays protected through this exact
construction and rendering path, per R10's existing recursive sink-scan
rules — no special-casing was needed. E14-5 itself adds no host transport
of any kind: the outbound transport capability (E14-6) and `web.http_send`
(E14-7) — documented next — were separate, later tickets — see
`GENIA_STATE.md` section 9.12 for the complete implemented contract.

E14-7 adds `web.http_send(operation, authority, timeout_ms)`: the first
outbound HTTP call actually reachable from Genia source, composing the
unchanged lifecycle core, `http_operation`, and the E14-6 transport
capability. Any status a real server returns comes back as an ordinary
success:

```bash
python3 -m http.server 8080 --bind 127.0.0.1 &
genia -c '
import web
op = http_operation(quote(get), "http://127.0.0.1:8080", "/", {}, {}, none("http-no-body")) |> unwrap_or(none)
response = unwrap_or(none, web.http_send(op, none("nil"), 2000))
display([response("status"), response("headers")("content-type")])
'
```

Output:

```text
"[200, text/html; charset=utf-8]"
```

A failure to obtain any response at all — here, nothing listening on the
target port — normalizes to a closed transport-failure reason instead of
raising past the call:

```bash
genia -c '
import web
op = http_operation(quote(get), "http://127.0.0.1:8081", "/", {}, {}, none("http-no-body")) |> unwrap_or(none)
display(web.http_send(op, none("nil"), 500))
'
```

Output:

```text
"err(\"http-transport-failure\", {kind: connect})"
```

A protected header (built the same way R10 already protects any secret)
stays protected through construction and can only be declassified by an
authorized `authority` immediately before the one transport attempt; a
missing authority is runtime misuse, not a normalized failure or a silent
leak:

```bash
genia -c '
import web
provider = config_provider([{kind: quote(values), values: {API_KEY: "s3cr3t-token"}}]) |> unwrap_or(none)
token = secret_get(provider, "API_KEY", quote(http_send)) |> unwrap_or(none)
op = http_operation(quote(get), "http://127.0.0.1:8080", "/", {authorization: token}, {}, none("http-no-body")) |> unwrap_or(none)
web.http_send(op, none("nil"), 2000)
'
```

Output:

```text
Error: http_send received a protected header with no authority; declassification requires some(authority)
```

Constructing a `GeniaDeclassificationAuthority` from ordinary Genia source
is not possible — exactly like R11's `model` credential/authority, it is
always an opaque, externally host-injected value, so the full
declassify-and-send round trip (a matching authority reveals the
credential only to the transport, never to any diagnostic or returned
response) is proven by `tests/unit/test_http_send.py`'s Python-host tests
rather than a plain `genia -c` example. E14-7 adds no `@get`/`@post`
annotation, no inbound server integration, no retry/redirect/pooling
machinery, and no automatic response decoding — `response.body` is always
an opaque bytes value the caller decodes explicitly — see `GENIA_STATE.md`
section 9.14 for the complete implemented contract.

E14-9 (#626) adds `@get {path}`/`@post {path}` — inert declarative
annotations — and `web.send_annotated(fn, base_url, authority,
timeout_ms)`, the sole function that binds them to the unchanged
`http_operation`/`web.http_send` surface:

```bash
python3 -m http.server 8080 --bind 127.0.0.1 &
genia -c '
import web

@get {path: "/"}
list_items() = {headers: {}, query: {limit: "5"}, body: none("http-no-body")}

result = web.send_annotated(list_items, "http://127.0.0.1:8080", none("nil"), 2000)
response = unwrap_or(none, result)
display([response("status"), response("headers")("content-type")])
'
```

Output:

```text
"[200, text/html; charset=utf-8]"
```

Annotating `list_items` never changes how it is called: ordinary call
syntax still just calls the function and returns its ordinary dynamic
`{headers, query, body}` map, performing no network IO —

```bash
genia -c '
@get {path: "/items"}
list_items() = {headers: {}, query: {limit: "5"}, body: none("http-no-body")}
display(list_items())
'
```

```text
"{headers: {}, query: {limit: 5}, body: none(\"http-no-body\")}"
```

— only the separate, explicit `web.send_annotated` call performs the one
transport attempt, composing exactly the unchanged `http_operation` and
`web.http_send`. A malformed target is a deterministic diagnostic, not a
silent no-op:

```bash
genia -c '
@get {path: "/x"}
config = {a: 1}
'
```

```text
Error: @get annotation requires a top-level named function
```

`@get`/`@post` share one cardinality slot per declaration, reuse
`@route`'s exact rebinding-rejection rules, and add no verb beyond these
two, no server `@route` replacement, and no new transport/lifecycle
mechanism of any kind — see `GENIA_STATE.md` section 9.16 for the
complete implemented contract. This is the first R14 ticket whose exact
shape the E14-0 contract did not itself lock (it names `@get`/`@post`
only as a future, unspecified E14-9 slice); the annotation payload,
target, and `send_annotated` composition above are this ticket's own
design, following `@route`'s established shape as closely as possible.

E14-10 (#627) proves R14's central composition claim — an inbound R8
server request can create outbound HTTP client lifecycle instances while
the server stays active — with **zero runtime-code change**: an R8 route
handler is an ordinary function, and `web.http_send` imposes no
caller-context precondition, so calling it from inside a handler already
composes correctly.

```bash
python3 -m http.server 8797 --bind 127.0.0.1 &
genia -c '
import web

handler(request) = {
  op = http_operation(quote(get), "http://127.0.0.1:8797", "/", {}, {}, none("http-no-body")) |> unwrap_or(none)
  result = web.http_send(op, none("nil"), 2000)
  status = unwrap_or(none, result)("status")
  web.json({downstream_status: status})
}

web.serve_http({host: "127.0.0.1", port: 8798, max_requests: 1}, web.route_request([web.get("/proxy", handler)]))
'
```

In another terminal:

```bash
curl -s http://127.0.0.1:8798/proxy
```

Output (the server's own result, printed after its one bounded request,
then the proxied response body):

```text
{host: "127.0.0.1", port: 8798, handled_requests: 1}
{
  "downstream_status": 200
}
```

The server's own `serve_http` result reports `handled_requests: 1` —
proving it completed the request normally even though the request's own
handler performed a full outbound HTTP round trip in the middle of
handling it. `tests/unit/test_http_server_client_composition.py` proves
the remaining acceptance shapes directly against real loopback servers:
the server stays active and completes a *second* request after an
outbound call fails (connect-refused) inside the first, contained by the
handler as an ordinary `err("http-transport-failure", {kind:
quote(connect)})` Outcome rather than crashing the request or the
server; one handler makes two sequential outbound calls in a single
request; and the same success shape composes identically through
`web.send_annotated`. No second server, routing, or CORS mechanism is
introduced — see `GENIA_STATE.md` section 9.17 for the complete proven
contract.

E14-11 (#695) proves the record-pipeline-adjacent claim this whole
contract is aimed at: `lifecycle_scope`, `lifecycle_repeat`, and
`lifecycle_context` (E14-1 through E14-3) already compose into a
repeated-record processing pipeline with **zero runtime-code change** —
`record`/`fields`/`nr`/`nf`-style values are derived as ordinary data from
the reserved `element`/`index` context, never as new AWK-style syntax.

```bash
genia examples/r14_repeated_record_lifecycle_proving_case.genia
```

```text
{summary: {eager_statuses: [ok, ok, ok, error, ok], survived_eager: [{id: "1", name: "Ada", status: "ok"}, {id: "2", name: "Grace", status: "ok"}, {id: "3", name: "Lin", status: "ok"}], survived_bounded: [{id: "10", name: "Amy", status: "ok"}, {id: "20", name: "Ben", status: "ok"}], bounded_count: 2}, log: [...]}
```

One outer pipeline/session `lifecycle_scope` wraps a `lifecycle_repeat`
call; every element gets a fresh scope with two peer
`LifecycleDefinition`s (`record_context`, `diagnostics`), entered and
reverse-unwound deterministically. Over an eager `List` source, a
data-level malformed record (wrong field count, returned as ordinary
`err(...)` data by `element_work`) and a genuine element work-phase
failure (a non-string element making `split` raise) are each recovered
from independently — every later element still processes, with no
cross-element context leakage (`eager_statuses` above:
`[ok, ok, ok, error, ok]`, element 4's exception never skipping element
5). Over a lazy `Flow` source bounded by `take`, each yielded element is
fully entered and unwound before the next pull — `bounded_count: 2`
confirms exactly two of the four available records were ever pulled, with
no over-pull. `survived_eager`/`survived_bounded` capture the
successfully classified records as ordinary values, using only existing
`filter`/`map` list operations. See `GENIA_STATE.md` section 9.18 for the
complete proven contract.

E14-12 (#628) proves the release's central vertical-HTTP claim: `config_view`/
`secret_view` (R13), `http_operation`/`web.http_send` (R14), the protected
HTTP header sink (R10), and `web.serve_http`/`web.route_request` (R8)
already compose into a complete end-to-end YouVersion Bible proxy proving
application, with **zero runtime-code change**. Minting a declassification
authority is a privileged host-side operation, never a pure-Genia one (the
same boundary `docs/releases/R13.md` already established), so a plain CLI
run only resolves configuration and shows the credential stays protected:

```bash
genia examples/r14_youversion_bible_proxy_proving_case.genia
```

```text
{base_url: "https://developers.youversionapi.com", version_id: "111", credential: "<protected>", protected_match: true}
```

The full outbound round trip — a real R8 server, a real local mock-upstream
fixture standing in for YouVersion, and a real injected authority — is
exercised entirely by
`tests/unit/test_r14_youversion_bible_proxy_proving_case_628.py`: a `POST
/passages` request carrying multiple canonical references produces one
outbound `web.http_send` call per reference, declassifying the credential
only immediately before transport (the mock upstream receives it; no
response, log, or audit record ever does), and returns a structured JSON
response with each reference's decoded passage or a deterministic error.
An upstream 5xx and a connect-refused upstream each normalize to an
ordinary per-reference `{status: "error", reason, ...}` value without
stopping the server from completing further requests — no real YouVersion
credential or public network dependency exists anywhere in the automated
tests. See `GENIA_STATE.md` section 9.19 for the complete proven contract.

E14-13 (#696) is the release's combined cross-cutting hardening gate,
proving -- again with **zero runtime-code change** -- that E14-1 through
E14-12 satisfy the full combined boundary that individual slice tests
cannot see on their own, following the same "conformance proof only"
shape as R13's own E13-5 hardening gate (`docs/releases/R13.md`).
`tests/unit/test_r14_cross_mode_hardening_696.py` proves: importing or
discovering (native-test mode) a module that defines but never invokes
`http_operation`/`@get`/lifecycle functions triggers zero outbound
transport calls; an `@get`-annotated route's own registration at server
startup never self-executes against a real downstream fixture; a
protected credential and ordinary lifecycle-context data survive

both cleanup failures landing in correct reverse-unwind order; `take(2)`
over a protected-value-carrying element scope pulls exactly two elements
with no leak; a raising transport's raw Python exception text never
reaches the normalized `err("http-transport-failure", {kind})` shape;
one request making both a successful and a failed outbound call,
followed by a second successful request against the same server, proves
combined resilience with no external network; and a parse-only check
confirms every R14 call form still parses via ordinary existing grammar,
with no new parser/AST/Core IR node. See `GENIA_STATE.md` section 9.20
for the complete proven contract.
