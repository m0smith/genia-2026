## Release purpose

Publish Genia as a small, governed Model Context Protocol server so MCP-capable clients can parse and run
Genia source **without acquiring new language semantics**. MCP is an adapter boundary over existing Genia, not
a second execution path. The product story: agent intent, an MCP tool call, the Genia parse and run boundary,
a structured result with diagnostics.

## Implemented architecture

- **Native Genia application:** `apps/mcp/mcp.genia` owns the protocol (newline-delimited JSON-RPC,
  MCP 2026-07-28, stateless), validation, tool schemas, dispatch, result envelopes, limits it owns, and
  cancellation matching.
- **Python reference-host capability boundary** (`hosts/python/`): a parse capability, a worker supervisor
  (disposable process per run, kill and reap, deadline, byte caps), a stdin line multiplexer, the restricted
  worker, and a launcher. Capabilities reach the Genia program as an explicit argument.
- **Local stdio** only. The repository-root `.mcp.json` registers one server, `genia`;
  `scripts/genia-mcp` starts the same launcher from any directory.

## Exactly three tools

`genia_capabilities`, `genia_parse`, `genia_run`, in that order. No MCP resources, no MCP prompts, no HTTP
transport, no C++ MCP implementation. Reference: `docs/mcp/reference.md`.

## Governed execution

Each `genia_run` call uses a fresh disposable worker: fixed minimal environment, private working directory,
process-group kill and reap, operating-system resource limits, a fixed 5,000 ms deadline, byte-exact limits,
a default-deny restricted Genia environment, static policy over the raw parser AST, runtime stubs, protected
values never crossing the boundary, and (where verified) a best-effort namespace. Program output is data and
cannot affect framing. This is a **defense-in-depth profile, not a security sandbox and not production
multi-tenant isolation**: `docs/mcp/security-and-deployment.md`.

## Protocol compatibility

Exactly two MCP revisions are served, both natively in `apps/mcp/mcp.genia` (contract amendment A5,
`docs/design/r28-genia-mcp-contract-threat-model.md` section 18): `2026-07-28` (stateless) and `2025-11-25`
(selected by `initialize`; one process-local state bit). Any other `initialize` version is rejected, not
negotiated down. Both eras reach the same three tools and the same governed execution model; client
capabilities grant no authority; no host code, tool, resource, prompt, limit, or authority was added
(ledger R28-H36). The amendment fixes the failure observed in run 1 but is not itself proof that VS Code now
completes the flow: that is run 2.

## Canonical demo: an Outcome-aware validated record pipeline

`docs/mcp/demo.md` takes a user from `git clone` to: start the server, connect a client, discover the three
tools, send a program with a mistake to `genia_parse`, read the diagnostic, repair it, parse it, and run it
through `genia_run`, getting clean records, one structured diagnostic per rejected record, and the value,
stdout, and stderr as separate channels. The programs are `examples/mcp/validated_records_broken.genia` and
`validated_records.genia`, use only implemented Genia, and are tested end to end.

```genia
valid_age(age) = age >= 0 && age <= 150

check(record) =
  validate_record(record, {
    id: (r) -> validate_required("id", r),
    name: (r) -> validate_required("name", r),
    age: (r) -> validate_field("age", valid_age, "age between 0 and 150", r)
  })

report = records |> ((items) -> validate_each(items, check)) |> collect_validated
```

## Packaging and entrypoint

The supported distribution is the repository checkout; `scripts/genia-mcp` is the executable entrypoint (no
arguments, any working directory, `uv` or Python 3.10+). `pyproject.toml`, the `genia` CLI, and the wheel are
unchanged: a console script or `genia mcp` would package `hosts/` and `apps/`, replace the git-derived
revision identity (ledger H10), and add a public CLI command, which are contract-level decisions outside this
release. No PyPI, npm, registry, or container publication is claimed.

## Host portability

Native Genia owns the protocol, validation, schemas, dispatch, envelopes, limits it owns, and cancellation
matching. The Python reference host owns parser and evaluator access, process supervision, hard kill and
reap, resource limits, stdin multiplexing, isolation mechanics, and bootstrap. **No C++ MCP support and no
cross-host MCP parity is claimed**; R28 does not prove MCP portability across hosts
(`docs/mcp/host-portability.md`).

## Known accepted limitations

Linux is the only platform with a passing evidence set. macOS: discovery, negotiation, capabilities, and parse worked in authentic VS Code, but governed execution failed there (H47; repair awaits macOS verification) and, even repaired, macOS has no address-space bound and no network namespace. Windows is unsupported (H43). A failed run returns
no diagnostic text and parse failures only a character offset (H42, H18). Values are canonical debug text
and callable values show host text (H32). UTF-16 surrogate escapes in strings do not cross the JSON boundary
unchanged (H40). A SIGKILLed host may leave an empty private temp directory. While more than 8 MiB of input is
pending, cancellation cannot be observed. The namespace layer is best effort. The final disposition of every
ledger entry is in `docs/analysis/r28-host-dependency-inventory.md` and
`docs/design/r28-e28-6-final-audit-plan.md`.

## What remains deliberately out of scope

Streamable HTTP, MCP resources and prompts, a C++ or Windows MCP host, an MCP client inside Genia, an agent
framework, general process supervision, a production multi-tenant sandbox, general FFI, legacy `initialize`
compatibility for any revision other than `2025-11-25` (older revisions are rejected, not negotiated), renderer or string-semantics redesign, and any new Genia syntax, builtin, or Core IR for MCP.
Issue #1078 (the 0.5 s spec-runner adapter timeout) is separate infrastructure work. The R20 follow-up
(#1067) stays scheduled after R28 and before R29.
