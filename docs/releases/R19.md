# R19 — Unicode and Diagnostic Portability

Status: **Complete — E19-1 through E19-5 (#826–#830) delivered. The
skeptical release truth audit (E19-6, issue #825) recorded a PASS verdict;
see `docs/analysis/r19-release-truth-audit.md`.**

R19 follows completed R17 Numeric and Ordered-Map Portability and R18
Portable Value Equality. Its purpose is to remove remaining Python-default
dependencies from byte-observable string and diagnostic surfaces before a
second production host implements them.

`GENIA_STATE.md` remains final authority. The approved contract is recorded
in `docs/design/r19-unicode-diagnostic-portability-contract.md`.

## Scope

R19 covers:

1. Portable Unicode/string semantics already exposed by existing Genia surfaces.
2. Deterministic string debug escaping.
3. The boundary between portable Genia diagnostics and host-local exception/error wording.
4. Shared conformance evidence sufficient for a non-Python host to implement those rules without consulting Python runtime behavior.

R19 explicitly does **not** include grapheme clusters, Unicode
normalization/collation, locale-aware formatting, Decimal/Rational/Float64
numeric-model work, approximate equality, a new error hierarchy, a public
diagnostic-code object system, Open Functions, or a C++ host implementation.
The former float-rendering blocker (F1) was split into a separate
exact-numeric-model workstream before implementation began (see
`docs/design/exact-numeric-model-preflight.md`).

## U1 — code-point semantics

A Genia string is an ordered sequence of Unicode scalar values.
`src/genia/utf8.py`'s internal `utf8_codepoints`/`utf8_safe_slice_by_codepoint`
iterate and slice by scalar value — never by UTF-8 byte and never by
grapheme cluster:

```python
>>> from genia.utf8 import utf8_codepoints, utf8_safe_slice_by_codepoint
>>> # "e" + U+0301 (COMBINING ACUTE ACCENT) is a single user-perceived
>>> # grapheme but two Unicode scalar values -- code-point semantics count
>>> # it as two, never one.
>>> combining_e_acute = "e" + "́"
>>> list(utf8_codepoints(combining_e_acute))
['e', '́']
>>> utf8_safe_slice_by_codepoint("abcdef", 1, 4)
'bcd'
>>> utf8_safe_slice_by_codepoint("abcdef", -2, None)
'ef'
>>> utf8_safe_slice_by_codepoint("abcdef", 4, 2)
''
```

Slice bounds normalize exactly: an omitted start is `0`, an omitted end is
the code-point length, a negative index counts from the end, a bound below
`0` after adjustment clamps to `0`, a bound above length clamps to length,
and a normalized `start >= end` yields the empty string. No implicit
Unicode normalization is performed, so canonically equivalent but
differently encoded sequences remain distinct values — this never changes
`==` (R18's equality contract is unaffected).

These helpers are internal to the Python reference host today; E19-1 added
no new public string-indexing syntax or slicing builtin, since none existed
to make portable.

## U2 — strict UTF-8 boundaries

`utf8_byte_length` and `utf8_is_boundary` (`src/genia/utf8.py`) report
UTF-8 byte length and whether a byte offset is a valid scalar boundary.
The public `utf8_decode` builtin decodes strict UTF-8 and fails
deterministically on malformed input, without implicit U+FFFD replacement
and without leaking raw host decoder wording:

```genia
utf8_decode(utf8_encode("hello 漢字 😀"))
-- "hello 漢字 😀"

utf8_decode(bad_bytes)   -- bad_bytes = the two invalid bytes 0xFF 0xFE
-- raises: utf8_decode invalid UTF-8 at byte offset 0
```

The message reports only the byte offset of the first invalid byte — a
portable integer fact any host can reproduce — never a Python-specific
decoder message.

## U3 — deterministic debug escaping

`format_debug` on a string surrounds it with ASCII double quotes and
applies deterministic escaping: the five short escapes (`\\`, `\"`, `\n`,
`\r`, `\t`), every other C0 control (`U+0000..U+001F`), DEL (`U+007F`), and
every C1 control (`U+0080..U+009F`) as lowercase `\uXXXX`; every other
Unicode scalar value renders literally. `format_display` remains the raw
character content with no surrounding quotes.

```genia
debug_repr("a\u0000b\nc\u007fd\u0080e")
-- "a\u0000b\nc\u007fd\u0080e"

debug_repr("é漢😀")
-- "é漢😀"
```

Neither rule depends on host terminal behavior, locale, or a Unicode
printability table.

## Diagnostic portability

E19-2 built a complete mechanical inventory
(`docs/analysis/r19-diagnostic-mechanical-inventory.md`) mapping every
`spec/error` exact-stderr case and genuine `spec/parse` failure case to
semantic family, construction site, interpolation/rendering approach, and a
proposed A/B/C classification (exact portable text / portable identity with
normalized rendering / host-local incidental detail, per the approved
contract).

That inventory found one confirmed host-`repr()` leak: a "No matching case"
runtime-dispatch failure interpolated Python's own `repr()` of the call
arguments. E19-3 fixed it:

```genia
f(x) = 1 -> "one"
f("hello")
-- before: Error: No matching case for function f/1 with arguments ('hello',)
-- after:  Error: No matching case for function f/1 with arguments ["hello"]
```

The new rendering uses Genia's own `format_debug` per argument (Genia's
list debug syntax), not Python's tuple-repr quoting convention. Every other
diagnostic family the inventory reviewed was already portable — in
particular the largest family ("expected X, received Y", 57 of 146 cases)
already renders via `_runtime_type_name`, a Genia-authored portable
type-name table, not Python `type()`/`repr`.

A lower-severity finding — Python `repr()`-style quoting of closed-grammar
source tokens (format-spec strings, lexer/parser token text) — was reviewed
and deliberately left unchanged, since it quotes a narrow ASCII grammar
token rather than an arbitrary runtime value; see the inventory document
§7 for the recorded reasoning.

E19-4 then swept the rest of `src/genia/*.py` for further leaks beyond the
two above. It found none that were both in scope and fixable with a small,
already-approved-rule change:

- `configuration.py`'s dotenv UTF-8 decode boundary and
  `gemini_rest.py`'s decode fallback were already fully U2-compliant.
- `evaluator.py`'s shell-pipeline subprocess stdout capture (`errors="replace"`)
  and `host_bridge.py`'s explicit `python.*` host-module exception wrapper
  are host-interop-by-design surfaces (external process output, and an
  explicit escape hatch into arbitrary Python code respectively) — reviewed
  and recorded as follow-up candidates for their own feature gates, not R19
  mechanical fixes.
- A handful of `src/genia/builtins.py` Outcome context-map fields
  (`read_file`/`write_file`/`zip_read`/`zip_write`/config-resource backends)
  carry a `message`/`detail` field built from `str(exc)`. These are
  explicitly **host-local incidental debugging detail (class C)**, not part
  of the portable diagnostic contract: the portable, asserted part of each
  such Outcome is its fixed `source`/reason string (e.g. `"read_file"`), and
  no shared spec case asserts the exact content of the `message`/`detail`
  field. A future contributor should not start pinning that field's exact
  text in a new shared spec case, since doing so would accidentally
  promote host-specific wording into the portable A/B boundary.

See `docs/analysis/r19-host-default-leak-audit.md` for the full sweep.

## Cross-release invariants preserved

R19 changed no R17 (ordered-map/integer), R18 (equality/map-key/protected/
opaque), R9 (JSON representation boundary), R10 (protected-value
non-leakage), or R16 (host-adapter outcome taxonomy) behavior. No Unicode
normalization changed `==`; no diagnostic improvement exposed a protected
payload; no runner/adapter outcome was reclassified as a Genia program
diagnostic.

## What R19 explicitly did not do

- No grapheme-cluster model, normalization, or locale-aware formatting.
- No Decimal/Rational/Float64 numeric-model implementation or rendering —
  that remains a separately gated exact-numeric-model workstream.
- No new public string API (no slicing/indexing syntax was added; U1's
  helpers remain internal, matching what existing Genia surfaces already
  exposed).
- No public diagnostic-code object system, message catalog, or
  localization framework.
- No Core IR change, no new syntax.
- No C++ host implementation.

  (code-point iteration/slicing including the contract's exact bound
  examples and a combining-sequence case), U2 (boundary queries, malformed
  UTF-8 failure), and U3 (short escapes, remaining C0/DEL/C1, literal
  non-control scalars).
- `spec/eval/r19-unicode-*.yaml` — 6 shared cases covering byte-length
  widths, `utf8_encode`/`utf8_decode` roundtrip, and debug-escaping at the
  Genia-language level.
- `tests/unit/test_r19_diagnostic_normalization.py` — 4 cases pinning the
  post-E19-3 "No matching case" rendering.
- 4 existing exact-stderr/eval cases deliberately updated to the new
  deterministic text (`error-pattern-miss`, `error-pattern-guard-all-fail`,
  `error-lambda-pattern-miss`, `first-on-flow-type-error`).

## Independent-host acceptance criterion

A non-Python host can reproduce U1/U2/U3 and the fixed diagnostic rendering
byte-for-byte from `docs/design/r19-unicode-diagnostic-portability-contract.md`
and this document's examples plus the shared evidence listed above, without
consulting Python `str` behavior, Python exception text, or Python source.

## Deferred items

- `evaluator.py` shell-pipeline subprocess stdout's `errors="replace"` and
  `host_bridge.py`'s `python.*` bridge exception wrapper (E19-4 follow-up
  candidates, not R19 issues — each belongs to its own feature's gate).
- The lower-severity format-spec/lexer-token `repr()`-style quoting
  convention (E19-3's recorded deferral).
- Any exact-numeric-model work (Decimal/Rational/Float64) — not part of R19.

## Release closure

E19-6's skeptical release truth audit (`docs/analysis/r19-release-truth-audit.md`)
re-derived every slice's claims from `main` as actually merged, re-ran full
regression and the shared-spec suite, verified the independent-host
acceptance criterion by direct reproduction attempt, and confirmed no
R17/R18/R9/R10/R16 regression and no exact-numeric-model behavior smuggled
in. **Verdict: PASS. R19 is complete.**

Dispatch**. R20's own contract gate has not been run; R19's completion does
not authorize R20 implementation to begin. The C++-host prerequisite set
(`docs/design/r21-cpp-host-preflight.md`) is unchanged by R19: R21 still
depends on R16, R17, R18, completed R19 (now satisfied), completed R20 (not
yet), and the separately gated exact-numeric-model contract (not yet
approved).
