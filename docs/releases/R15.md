# R15 — Validated Value Modeling

Status: **Active — E15-0 contract approved (#726/#738); E15-1 (#728) through E15-7 (#734) delivered**

R15 extends the completed R9 Value Template / representation model into a
more practical validated-value toolset. Delivered APIs remain
**Experimental**. See `docs/design/r15-validated-value-modeling-contract.md`
for the full approved release boundary and `GENIA_STATE.md` for final
implemented truth.

## E15-1 — Inert inspectable Template descriptions

Run:

```bash
genia -c 'Person = exact_shape({name: refinement((x) -> x != ""), age: refinement((x) -> x >= 0)})
[Person({name: "Ada", age: 3}), template_description(Person)]'
```

Output:

```text
[some({name: "Ada", age: 3}), some({kind: exact_shape, fields: {name: {kind: refinement}, age: {kind: refinement}}})]
```

`refinement(predicate)`, `open_shape(fields)`, and `exact_shape(fields)` are
curried one-argument Template builders with the same matching behavior as
the existing `refinement_match`/`open_shape_match`/`exact_shape_match`
helpers. Templates they build — and Templates `json_schema` compiles — carry
an inert, host-independent description that `template_description(template)`
returns as `some(description)`. Every other callable Template, including
arbitrary callables and named patterns declared with
`pattern Name(value) = ...`, remains fully valid but opaque and returns
`none("opaque-template")`.

Construction and inspection perform no effects: no user-data validation
runs, no predicate is executed, and no config/lifecycle/IO/import-time
activation occurs. Descriptions never affect callable identity, equality,
matching, dispatch, or `@?`/`@!`/`&` original-subject semantics.

E15-1 adds no defaults, diagnostics accumulation, schema generation,
structural alternatives, recursion, or new parser/Core IR surface — those
remain later R15 slices (#729 through #736).

## E15-2 — Explicit missing-only field defaults and normalization

Run:

```bash
genia -c 'Config = open_shape({host: default_field("localhost", refinement((x) -> x != "")), port: default_field(8080, refinement((x) -> x > 0))})
[Config({}), Config({port: 9000})]'
```

Output:

```text
[some({host: "localhost", port: 8080}), some({port: 9000, host: "localhost"})]
```

`default_field(default, template)` wraps a field Template with an explicit
default for use inside `open_shape`/`exact_shape`. A present field is
always validated by `template` and never falls back to the default,
including a present invalid value. A missing field validates `default`
itself through `template` before inserting it; a shape with no applied
defaults returns the exact original subject unchanged, while one with
applied defaults returns a new map extending it.

`template_description` on a `default_field`-wrapped Template records only
that a default exists (`has_default: true`) — never the literal default
value — so a protected or represented default stays opaque. Explicit
normalization needs no new builtin: `record |> normalize_fn |> Shape` is
already ordinary explicit pipeline composition, and Template matching
itself performs no coercion.

E15-2 adds no accumulated diagnostics, schema generation, structural
alternatives, or recursion — those remain later R15 slices (#730 through
#736).

## E15-3 — Accumulated path-aware validation diagnostics

Run:

```bash
genia -c 'Person = exact_shape({name: refinement((x) -> x != ""), age: refinement((x) -> x >= 0)})
accumulate(Person, {name: "", age: -1})'
```

Output:

```text
err(accumulated-validation-failed, {diagnostics: [{path: ["name"], kind: mismatch, reason: "refinement-mismatch"}, {path: ["age"], kind: mismatch, reason: "refinement-mismatch"}]})
```

`accumulate(template, value)` validates `value` against an inspectable
Template and collects every independent field/index failure in one call,
instead of stopping at the first mismatch. It recurses depth-first into
nested `open_shape`/`exact_shape` structure (including `default_field`
fields, which keep their real default-insertion behavior); a bare
`refinement` or other inspectable Template is one leaf check. Each
diagnostic is `{path, kind, reason}`, where `path` is built only from the
Template's own specification and `reason` never carries the underlying
Outcome's context — so a protected or represented payload can never leak
through a diagnostic. Zero diagnostics returns the exact real Template
success value (defaults included); one or more returns
`err(quote(accumulated-validation-failed), {diagnostics})`.

`accumulate` changes no pattern-dispatch, `@?`/`@!`/`&`, or Template
direct-call semantics, and touches no Flow/Seq state itself — composing it
inside an ordinary `map` stage over a lazy Flow preserves existing
bounded-demand, no-over-pull behavior.

E15-3 adds no schema generation, structural alternatives, or recursive
Template references — those remain later R15 slices (#731 through #736).

## E15-4 — Faithful Template to JSON Schema generation

Run:

```bash
genia -c 'name_schema = represent("json", {type: "string"})
NameTemplate = json_schema(name_schema) |> unwrap_or((_) -> none("compile-failed"))
Person = exact_shape({name: NameTemplate})
template_schema(Person) |> unwrap_or((_) -> none("failed")) |> strip_representation("json")'
```

Output:

```text
{type: "object", properties: {name: {type: "string"}}, required: ["name"], additionalProperties: false}
```

`template_schema(template)` is the bounded reverse of `json_schema`: pure
inspection over `template_description` data that never invokes `template`,
never invokes a nested field Template, and never executes a callable
refinement predicate. A `json_schema`-compiled Template's own description,
and any `open_shape`/`exact_shape` whose fields all recursively convert,
generate a faithful schema.

An opaque Template, a bare `refinement` field (its predicate is never
introspected, so it has no derivable JSON type), or a `default_field`
(JSON Schema's `default` is an annotation, not an insertion transform) fail
deterministically as `err(quote(unsupported-template), {path, kind})`
rather than approximating. Round-trip claims (`json_schema` →
`template_schema` → `json_schema`) are limited to accept/reject equivalence
over the tested subset.

E15-4 adds no structural alternatives or recursive Template references —
those remain later R15 slices (#732 through #736).

## E15-5 — Structural discriminated alternatives

Run:

```bash
genia -c 'Circle = open_shape({radius: refinement((x) -> x > 0)})
Square = open_shape({side: refinement((x) -> x > 0)})
Shape = alternatives("kind", {circle: Circle, square: Square})
[Shape({kind: "circle", radius: 5}), Shape({kind: "triangle", a: 1})]'
```

Output:

```text
[some({kind: "circle", radius: 5}), none("alternative-unknown-discriminator", {field: "kind", value: "triangle"})]
```

`alternatives(discriminator_field, branches)` selects exactly one branch by
reading an explicit string discriminator field, then validates only that
branch against the full original value. Payloads remain ordinary Genia
maps — no nominal variant object is ever constructed. Missing, invalid, or
unknown discriminators produce deterministic `none(...)` diagnostics; a
branch's own mismatch/error surfaces unchanged and no other branch is ever
attempted.

`alternatives` composes with named patterns, `@?`/`@!`/`&`, `accumulate`,
and `template_description` automatically, since it produces an ordinary
Template built the same way as `refinement`/`open_shape`/`exact_shape`.
`template_schema` reports it as deterministically unsupported, since
E15-4's closed JSON Schema keyword subset has no discriminated-union
primitive.

This slice absorbs only the structural-validation portion of issue #92.
Nominal variant identity, constructor objects/syntax, sealed/closed nominal
hierarchies, and exhaustiveness checking remain explicitly deferred and are
not implemented.

E15-5 adds no recursive Template references — that remains the final R15
implementation slice (#733).

## E15-6 — Bounded named recursive Template references

Run:

```bash
genia -c 'Tree = recursive_template("tree", (ref) -> alternatives("kind", {
  leaf: exact_shape({kind: refinement((x) -> x == "leaf")}),
  node: exact_shape({kind: refinement((x) -> x == "node"), value: refinement((x) -> true), left: ref("tree"), right: ref("tree")})
}), 5)
valid = {kind: "node", value: 1, left: {kind: "leaf"}, right: {kind: "node", value: 2, left: {kind: "leaf"}, right: {kind: "leaf"}}}
Tree(valid)'
```

Output:

```text
some({kind: "node", value: 1, left: {kind: "leaf"}, right: {kind: "node", value: 2, left: {kind: "leaf"}, right: {kind: "leaf"}}})
```

`recursive_template(name, build_fn, max_depth)` builds a self-recursive
Template through one explicit named reference. `build_fn(ref)` runs
exactly once at construction; `ref(name)` returns a self-reference
Template, while requesting any other name always fails deterministically
as `err("recursive-template-unresolved-reference", {name})` — proving
deterministic unresolved-reference behavior without implementing general
mutual recursion.

Depth is tracked per instance with a dedicated, non-shared counter capped
at `max_depth` (at most 100), so recursing beyond the bound fails with
`err("recursive-template-depth-exceeded", {limit})` before ever invoking
the wrapped structure further — this operation's own explicit bound always
fires well inside Python's own recursion limit; no host `RecursionError`
ever crosses the boundary. Reference resolution is closed entirely over
the construction-time triple: no mutable global registry, configuration,
or lifecycle context ever participates.

`accumulate` and `template_schema` both treat a `recursive_template`
Template as one leaf check at every level — a deliberate, documented
boundary rather than a gap, avoiding a second independently-bounded
traversal inside either operation. Direct-call validation is unaffected
and performs real bounded recursive traversal over ordinary tree-shaped
data; subjects are never treated as runtime object graphs.

E15-6 completes R15's implementation slices.

## E15-7 — Composed messy-record validated-data proving case

Run:

```bash
genia examples/r15_composed_messy_record_proving_case.genia
```

Output:

```text
{valid_order: some({customer_name: "Ada Lovelace", email: "ada@example.com", payment: {method: "card", last4: "4242"}, history: {kind: "entry", order_id: "A100", previous: {kind: "none"}}, items: [{sku: "WIDGET-1", qty: 3, price: 9.99}, {sku: "GADGET-2", qty: 2, price: 4.5}], country: "US"}), messy_order: err(order-validation-failed, {envelope: [{path: ["customer_name"], kind: mismatch, reason: "refinement-mismatch"}, {path: ["email"], kind: mismatch, reason: "refinement-mismatch"}, {path: ["payment", "method"], kind: mismatch, reason: "alternative-unknown-discriminator"}, {path: ["history"], kind: mismatch, reason: "alternative-unknown-discriminator"}], items: [{index: 1, kind: skipped, reason: "parse-error", context: some({source: "parse_int", expected: "integer_string", received: "abc", base: 10})}, {index: 2, kind: skipped, reason: "json-schema-type-mismatch", context: some({path: [], expected: number, actual: string})}]}), too_deep_order: err(order-validation-failed, {envelope: [{path: ["history"], kind: error, reason: "recursive-template-depth-exceeded"}], items: []}), item_schema: {type: "object", properties: {sku: {type: "string"}, qty: {type: "integer"}, price: {type: "number"}}, required: ["sku", "qty", "price"], additionalProperties: false}, envelope_schema: err(unsupported-template, {path: ["customer_name"], kind: refinement})}
```

E15-7 proves that E15-1 through E15-6 compose into Genia's killer workflow
rather than forming isolated validation helpers, using only previously
landed R15 behavior plus existing Genia primitives. One composed order
record demonstrates every required mechanism at once: explicit
`trim`/`parse_int` decode and normalization ahead of non-coercive Template
validation; a missing-only `default_field` country default; `accumulate`
producing deterministic path-aware diagnostics across several
independently invalid `customer_name`/`email`/`payment`/`history` fields
in one call; a discriminated `alternatives` payment method; a bounded
`recursive_template` linked order-history chain, including its explicit
`recursive-template-depth-exceeded` bound; a faithful `template_schema`
success for a `json_schema`-derived item Template paired with a
deterministic `unsupported-template` failure for a Template containing a
bare `refinement` field (never approximated); and composition with
existing `validate_each`/`collect_validated` Outcome-aware pipeline
behavior for the order's line items. A corrected order composes into one
ordinary Genia value with the default applied and items decoded, ready
for normal pipelines. This fixture contains no protected values; the
opacity guarantee for a protected/represented value already proven by
E15-1's and E15-3's own tests (a description or diagnostic can only ever
record inert shape/path/reason data, never a value) applies unchanged were
one introduced later.

E15-7 adds no runtime code: every mechanism it composes was already landed
by #728 through #733, and every value shown above was executed and
verified against the interpreter, not hand-derived. #735
(cross-mode/portability hardening) and #736 (documentation, final truth
audit, and distillation) remain.
