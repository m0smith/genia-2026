# R16 — Multi-Host Conformance Infrastructure

Status: **Complete — E16-0 contract approved (#757); E16-1 through E16-7
(#758-#764) delivered. Skeptical release truth audit (E16-8, #765)
recorded a PASS verdict.**

R16 gives independently versioned host repositories one honest, repeatable
way to prove conformance against the authoritative `genia-2026` contract.
It is infrastructure only: it changes no Genia language or Core IR
behavior. See
`docs/design/r16-multi-host-conformance-infrastructure-contract.md` for
the full approved wire-level contract and `GENIA_STATE.md` §0 for final
implemented truth.

**The critical truth this release does not change:** Python remains the
only implemented **production** host. R16 builds the generic protocol,
runner, capability, revision, and evidence machinery a second host would
use — and proves that machinery end-to-end against the Python reference
host and a non-semantic bootstrap placeholder — but no real second
production interpreter exists yet. That is R21.

## E16-1 — Versioned host-adapter protocol and failure taxonomy

Run:

```bash
python -m tools.spec_runner --host 'python3 -m tools.spec_runner.fixtures.protocol_fixture_adapter' --host-timeout 5
```

The deterministic, non-semantic fixture adapter (not a Genia host) proves
every outcome in the taxonomy end-to-end: a valid `ok`/`unsupported`
response, protocol-version mismatch, `case_id`/`operation` mismatch, an
invalid envelope shape, a process crash, a timeout, and — the roadmap's
explicitly named risk — an adapter that lets non-envelope text reach its
own stdout, which is classified `PROTOCOL ERROR` rather than silently
accepted. `tools/spec_runner/protocol.py` implements the envelope; an
adapter can only ever self-report `ok` or `unsupported`, never
`protocol_error`/`crash`/`timeout` — those are always derived by the
runner from process/JSON facts.

## E16-2 — Generic external-host execution path in `tools/spec_runner`

Run:

```bash
python -m tools.spec_runner --host 'python3 -m tools.spec_runner.fixtures.protocol_fixture_adapter' --host-timeout 5
```

Output (tail):

```text
Summary: total=641 passed=0 failed=623 unsupported=18 protocol_error=0 crash=0 timeout=0 invalid=0
```

Running the entire real `spec/` suite through the deterministic fixture
adapter is a transport/taxonomy proof, not a conformance claim: `passed=0`
because the fixture is not a Genia host and correctly never claims
otherwise; `unsupported=18` is exactly the cases needing an injected
Python-host-only test fixture or `--debug-stdio`, neither expressible over
the generic protocol yet; `protocol_error=0`/`crash=0`/`timeout=0` proves
the runner handles every category cleanly with zero host-specific
knowledge. `python -m tools.spec_runner` (no `--host`) still reports
`641/641` — the in-process default path is unchanged.

## E16-3 — Host capability advertisement and per-case requirements

Adds a mandatory `capabilities` protocol operation and an optional per-case
`requires:` field. `--host` mode fetches and validates a host's capability
declaration once per run, before any case executes; a case requiring a
capability the host does not declare exactly `supported` is reported
`unsupported` without invoking the adapter for it — never silently skipped
or counted as passing. No shared spec case currently declares `requires`;
this lands the mechanism, not new coverage. See
`tools/spec_runner/capabilities.py`.

## E16-4 — Contract revision pinning and current-main compatibility reporting

Run:

```bash
python -m tools.spec_runner --host 'python3 -m tools.spec_runner.fixtures.protocol_fixture_adapter' --host-timeout 5
```

Output (head):

```text
Revision: pinned conformance for <sha> (host-declared revision matches this checkout exactly)
```

`tools/spec_runner/revision.py` classifies a host's declared
`contract_revision` against this checkout's actual revision using local
git history only: an exact match is honest pinned-conformance evidence; a
real older commit is current-main-compatibility-only evidence (a host may
be correctly conforming to its declared revision while visibly behind
current `main` — expected, not an error); a revision this checkout has
never seen stops the run with exit code 1 before any case executes.

## E16-5 — Python reference host through the subprocess protocol

Run:

```bash
python -m tools.spec_runner --host 'python -m hosts.python.protocol_adapter' --host-timeout 30
```

Output (tail):

```text
Summary: total=641 passed=623 failed=0 unsupported=18 protocol_error=0 crash=0 timeout=0 invalid=0
```

`hosts/python/protocol_adapter.py` exposes the Python reference host
itself as an E16-1 protocol-speaking subprocess command — real Genia
evaluation through two full subprocess hops per `eval`/`cli` case, not the
fixture. The result is identical to the in-process default path for every
applicable case. The in-process path is retained unchanged as a
developer-optimization path, not the conformance definition; the
subprocess protocol above is what any host, Python included, is actually
held to.

Run:

```bash
python -m tools.spec_runner --host 'python3 <genia-cpp checkout>/bootstrap/protocol_adapter_stub.py' --host-timeout 5
```

Output (tail):

```text
Summary: total=641 passed=0 failed=0 unsupported=641 protocol_error=0 crash=0 timeout=0 invalid=0
```

[`m0smith/genia-cpp`](https://github.com/m0smith/genia-cpp) is bootstrapped
as the first external production-host repository: a repository shell
(`README.md`/`AGENTS.md` naming `genia-2026` as sole authority, a pinned
contract revision and E16-1 protocol version declaration) with **no real
C++ interpreter**. Its `bootstrap/protocol_adapter_stub.py` is a minimal,
self-contained placeholder — no runtime dependency on `genia-2026`'s
Python package — that answers every operation `unsupported`
deterministically; it does not interpret Genia source at all. `hosts/cpp/`
in this repository transitioned to a pointer (`hosts/cpp/README.md`) so no
duplicate authoritative-looking C++ implementation exists in two places.

## E16-7 — Conformance evidence reporting and external-host CI contract

Run:

```bash
python -m tools.spec_runner --host 'python -m hosts.python.protocol_adapter' --evidence /tmp/evidence.json
cat /tmp/evidence.json
```

Output (evidence document, real values from this exact release):

```json
{
  "applicable_cases": 641,
  "capabilities": { "parser": "supported", "shared_spec_runner": "partial", "...": "..." },
  "capability_operations": ["parse", "lower", "eval", "cli"],
  "contract_revision": {
    "checkout": "<sha>",
    "classification": "current",
    "declared": "<sha>"
  },
  "counts": {
    "crash": 0, "fail": 0, "invalid": 0, "pass": 623,
    "protocol_error": 0, "timeout": 0, "unsupported": 18
  },
  "protocol_version": "1",
  "total_cases": 641
}
```

`tools/spec_runner/evidence.py::build_evidence` is a pure function of its
inputs — `encode_evidence` serializes with `sort_keys=True`, so identical
runs produce byte-identical evidence — and raises rather than publish a
document whose counts do not sum to the total. No evidence is written when
the run stops before any case executes. The same model was proven against
the `genia-cpp` bootstrap placeholder too (`641` unsupported, revision
classified `resolvable_ancestor`), honestly distinguishing pinned
conformance from current-main-compatibility-only for both hosts.
`docs/strategy/roadmap/multi-host-conformance-policy.md`'s "Evidence model
and CI expectations" records the external-host CI contract this defines:
pin a revision, run the generic protocol, publish the evidence artifact,
fail the job on the runner's exit code (never on `unsupported` alone), and
separately run a non-blocking current-`main` drift check.
