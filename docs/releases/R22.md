# R22 — Exact Numeric Runtime

Status: **Slices E22-1 through E22-9 merged to `main`.** E22-10 (this
document) synchronizes documentation with what has actually landed;
`GENIA_STATE.md` sections 9.23–9.31 remain final authority for implemented
behavior, and this document summarizes it. R22 is not yet release-complete
-- completion is decided by E22-11's fresh skeptical release truth audit
(issue #897), not by this document.

R22 follows completed R21 (`docs/releases/R21.md`) and makes Genia's
runtime numeric value model exact by default, with Float64 an explicit,
separate approximate domain. It consumes R21's numeric source
classification and tagged portable `IrLiteral` payloads without reopening
them.

The approved contract is
`docs/design/r22-exact-numeric-runtime-contract.md`.

## Scope

R22 owns:

1. Runtime **Decimal** (`GeniaDecimal`) and runtime **Rational**
   (`GeniaRational`) values, and explicit **Float64** (a bare host
   `float`) as a separate approximate domain.
2. Exact-family arithmetic `+`, `-`, `*` over the `Integer < Decimal <
   Rational` promotion lattice.
3. Exact division `/` and floor remainder `%`, each with their own
   promotion/termination rules (section 7 and 8 of the contract).
4. `rational(numerator, denominator)`, `float64(value)`, `exact(value)`.
5. Rejection of arithmetic mixing Float64 with any exact-family operand.
6. Mathematical cross-kind equality/comparison (Integer/Decimal/Rational
   compare by mathematical value; a finite Float64 bridges to an exact
   value by its own exact represented value) integrated into the single
   R18 equality/map-key architecture -- no second equality relation.
7. Deterministic numeric misuse (division/remainder by zero, invalid
   `rational`/`float64`/`exact` arguments, mixed-domain arithmetic) and a
   private, non-public `numeric-resource-limit` bound.
8. Cross-surface compatibility hardening: quoted/metacircular evaluation,
   pattern matching, Sheets, and retrieval scoring all preserve
   Decimal/Rational kind and value exactly as ordinary evaluation does.

R22 explicitly does **not** own: canonical display/debug spelling,
field-format presentation, JSON numeric transport policy, new numeric
literal syntax, transcendentals/ambient precision, or a C++ host. Those
remain R23 and R24.

## Exact arithmetic

```genia
1.5 + 2.25
-- 3.75  (Decimal)
```

Decimal participation retains Decimal kind for `+`, `-`, `*` even when the
mathematical result is integral; Rational results are always reduced, and
a denominator-one Rational collapses to Integer.

## Exact division and floor remainder

The contract's own six required proof examples (section 7):

```genia
[6 / 3, 1 / 2, 1 / 3, 1.0 / 2, 1.0 / 3, (1 / 3) * 3]
-- [2, 1/2, 1/3, 0.5, 1/3, 1]
```

Pure Integer/Integer division is Integer-or-Rational only -- it never
becomes Decimal, even when the quotient terminates in base 10 (`1.0 / 3`
still becomes Rational `1/3` because Decimal participation only stays
Decimal when the quotient *terminates* in base 10; `1/3` does not).
Division by exact zero is deterministic numeric misuse, not an implicit
Decimal/Rational result.

## `rational(...)`, `float64(...)`, `exact(...)`

```genia
rational(1, 3)
-- 1/3

float64(rational(1, 3))
-- 0.3333333333333333   (Float64, round-to-nearest ties-to-even)

exact(float64(0.1))
-- 0.1000000000000000055511151231257827021181583404541015625
```

`exact(...)` recovers the real dyadic value a finite Float64 bit pattern
represents -- not merely a spelling that round-trips back to that Float64.
`float64(...)` fails rather than silently producing infinity when the
exact magnitude exceeds the largest finite binary64 value; `exact(...)`
fails on NaN and infinity rather than producing a placeholder Decimal.

## Mixed exact/Float64 rejection

Arithmetic mixing Float64 with any exact-family operand is rejected in
both operand orders -- the caller must choose a domain explicitly with
`float64(...)` or `exact(...)` first:

```genia
1 + float64(2)
-- none("type-error", {source: "+", left: "int", right: "float"})
```

This bridge exists only for equality/comparison, never arithmetic.

## Mathematical cross-kind equality

Integer, Decimal, and Rational compare by mathematical value, and a finite
Float64 bridges to an exact value by its own exact represented value
(never by rounding the exact operand to Float64):

```genia
[1 == 1.0, 1.0 == 1.00, 1 == rational(2, 2), rational(1, 2) == 0.5]
-- [true, true, true, true]
```

This is the same single R18 equality/map-key relation used everywhere
else in the language -- no second, numerically-approximate equality is
introduced. NaN remains unequal to everything including itself and is not
a legal map key, matching R18 unchanged.

## Deterministic numeric misuse and resource limits

Division/remainder by zero (exact or Float64), invalid `rational`/
`float64`/`exact` arguments, and mixed-domain arithmetic all fail with a
clean, deterministic diagnostic -- never raw host exception text. A
private, non-public `numeric-resource-limit` bound (a host/test
implementation detail, never part of shared conformance) guards
`GeniaDecimal`/`GeniaRational` construction against unbounded coefficient/
numerator/denominator magnitude; it never applies to plain R17 Integer
arithmetic, which remains fully unbounded.

## Cross-surface compatibility

Every numeric-touching surface outside the evaluator's core arithmetic
dispatch was audited (E22-9) to confirm it preserves R22 kind/value
exactly as ordinary evaluation does: `quote(1.5)`, `quasiquote(1.5)`, and
metacircular `eval(...)` of a Decimal or Rational value all produce the
same `GeniaDecimal`/`GeniaRational` ordinary evaluation would, not a
Float64 stand-in; literal-pattern matching (`case_expr`-style function
clauses) uses the same mathematical equality relation as `==`; Sheets
`render_csv` and retrieval evidence-score finiteness gating both accept
Rational alongside Decimal.

## Shared evidence

Shared `spec/eval/*` and `spec/error/*` conformance cases cover exact
arithmetic, exact division/remainder, `rational`/`float64`/`exact`,
mixed-domain rejection, cross-kind equality/map-key reconciliation,
numeric misuse, and cross-surface (quoted/pattern-matching) conformance.
`tests/spec/test_python_protocol_adapter_parity_762.py` proves every
applicable case passes identically through both the in-process Python
path and the generic subprocess protocol adapter.
