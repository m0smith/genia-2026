# R25–R28 — C++ Host Expansion and MCP Server

Status: Planned roadmap detail — non-authoritative. `GENIA_STATE.md` remains final authority for implemented behavior.

R25-R27 continue the C++ host arc after R24. R28 is the Genia MCP Server release, preserving the previously planned MCP work as a first-class roadmap item.

## Release R25 — C++ Stateful Runtime and Concurrency

**Status: Planned, not active.** Depends on R24.

Theme: add stateful C++ capabilities only after ownership, cycles, cleanup, and concurrency observations are explicit.

Candidate scope retains the prior plan: C++ ownership/lifetime strategy; portability promotion for refs/cells/process observations; threading/mailbox/failure/cleanup mapping; deterministic stress/race/lifecycle tests; evidence-based capability claims; no language scheduler, async/await, supervision tree, distributed actors, HTTP, or resource IO.

## Release R26 — C++ REPL and Data Bridges

**Status: Planned, not active.** Depends on R24; bridge tracks remain separately gated.

Theme: extend the minimal host with interactive evaluation and deterministic data boundaries.

Candidate scope retains the prior plan: REPL behavior plus promoted bytes/UTF-8, strict JSON, and ZIP boundaries; duplicate-key rejection, JSON safe ranges, Unicode validation, nesting limits, deterministic output, normalized Outcomes/errors, and R16 capability-tagged evidence. Pipe mode/Flow and HTTP remain later.

## Release R27 — C++ Flow, Pipe Mode, and HTTP Serving

**Status: Planned, not active.** Depends on R24 and on any R25/R26 behavior actually required by approved designs.

Theme: complete the largest remaining portable runtime surfaces without turning C++ internals into Genia semantics.

Candidate scope retains the prior plan: lazy pull-based single-use Flow phase 1, `-p`/pipe mode over Flow, explicitly promoted HTTP/server contracts, R8 lifecycle/server behavior, capability-aware differential evidence, and honest unsupported classifications.

## Release R28 — Genia MCP Server

**Status: Planned, not active.** Integration infrastructure; it adapts implemented Genia behavior and must not define a second semantics path.

Theme:

> Publish Genia as a small, governed Model Context Protocol server so MCP-capable hosts can inspect and invoke Genia through explicit, structured boundaries.

Planned v1 surface:

- `genia_parse` — explicit source input to existing parse/normalization behavior
- `genia_run` — governed explicit source execution through approved host execution paths
- `genia_capabilities` — stable adapter/host capability and limitation reporting
- stdio as the required local transport
- Streamable HTTP only if the contract/threat-model gate proves it does not widen authority or imply a production multi-tenant sandbox
- deterministic structured separation of returned value, emitted output, diagnostics, protocol failures, parse failures, runtime failures, and policy rejection
- explicit timeout/cancellation/result-size rules
- protected config/secret redaction and no ambient filesystem/environment authority
- official MCP client/SDK integration tests and parity tests against direct Python-reference-host behavior
- one runnable Outcome-aware validated-data-pipeline demo

Safety/authority boundaries:

- no arbitrary host filesystem browsing
- no arbitrary shell execution
- no implicit environment/secret exposure
- no new Genia syntax or Core IR solely for MCP
- no autonomous agent/tool orchestration inside Genia
- no silent promotion of Python-host-only behavior into portable language semantics

Critical acceptance criterion:

- An ordinary MCP client can discover the server, parse and run a small Genia validated-data-pipeline program, receive deterministic structured results/diagnostics, and observe behavior consistent with direct approved host execution.

Existing GitHub planning epic #700 and its E24-* subtasks are renumbered to R28/E28-* as part of planning issue #845; their substantive MCP scope remains the starting point for the R28 contract gate.
