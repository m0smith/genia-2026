# R41 — Portable Core IR Artifacts

Status: Planned roadmap detail — non-authoritative. `GENIA_STATE.md` remains final authority for implemented behavior.

## Release R41 — Portable Core IR Artifacts

**Status: Planned, not active.** R41 is infrastructure work that promotes the existing Core IR portability boundary into a stable deployable artifact contract. It does not add implemented behavior merely by appearing on the roadmap.

Theme:

> A conforming Genia runtime host can validate and execute a supported portable Core IR artifact without requiring a Genia source compiler.

### Why this belongs on the roadmap

R16 established the multi-host conformance boundary and later portability releases made Core IR the language/host semantic boundary. The missing deployment boundary is a stable file representation that can be produced once and consumed by independent hosts.

This directly supports Genia's location-independent and multi-host direction: application semantics stay in Genia/Core IR while compilation becomes a toolchain concern rather than a mandatory runtime-host feature. It is infrastructure rather than a replacement for the Outcome-aware validated-data-pipeline north star.

A deliberately compiler-free first browser host is a motivating proving consumer: it should be possible for such a host to load, validate, link, and interpret a portable artifact without carrying the Genia lexer, parser, or source-to-Core-IR lowering pipeline. Browser implementation itself is not part of R41.

### Architectural boundary

R41 must preserve one IR boundary:

```text
Genia source
    |
    v
compiler / toolchain
    |
    v
Core IR
    |
    v
portable artifact serialization
    |
    +--> Python host
    +--> C++ host
    +--> future browser host
```

The portable artifact is a stable serialization/container for supported Core IR. It is **not** a second semantic IR between Core IR and host-local execution structures.

### Candidate release slices

1. **R41-0 — Artifact logical model and compatibility contract**
   - define module identity, imports/exports, constants, supported Core IR payload, annotations/debug mappings where justified, and declared capability requirements;
   - define independent `artifact_format_version` and `semantic_contract_version`;
   - define compatibility and rejection rules;
   - keep encoding choice separate from the semantic model.

2. **R41-1 — Validation and trust-boundary contract**
   - bytes/container validation;
   - format-version validation;
   - Core IR structural validation;
   - semantic-contract validation;
   - import/link validation;
   - capability-requirement validation;
   - stable normalized failure categories with no host exception leakage.

3. **R41-2 — Canonical reference serialization**
   - choose the simplest deterministic reference representation sufficient to prove the model;
   - prefer an inspectable/canonical representation before freezing a compact binary encoding;
   - define deterministic ordering and canonical round-trip expectations.

4. **R41-3 — Python artifact writer/loader**
   - compile supported Genia source to Core IR and emit the reference artifact;
   - reload the artifact into equivalent supported Core IR;
   - execute through the existing Python runtime without reparsing source.

5. **R41-4 — Second-host artifact loader**
   - consume the same artifact in the C++ host;
   - validate the same compatibility/capability rules;
   - execute the supported shared semantic subset without a source compiler in the C++ artifact path.

6. **R41-5 — Cross-host artifact conformance corpus**
   - source -> Core IR -> artifact -> reload equivalence evidence;
   - shared artifacts checked into the authoritative conformance corpus where appropriate;
   - Python/C++ normalized outcomes must agree for the supported capability set;
   - malformed/version-incompatible artifacts must fail consistently.

7. **R41-6 — Packaging and execution surface**
   - define the explicit CLI/toolchain operations for producing, inspecting, validating, and executing artifacts;
   - keep compilation optional for runtime hosts;
   - keep host capabilities explicit rather than ambient.

8. **R41-7 — Compact binary-format decision gate**
   - use evidence from the reference format and cross-host implementation before freezing a binary representation;
   - if a binary format is justified, specify section/chunk extensibility, deterministic encoding, unknown-section policy, size/resource bounds, and forward/backward compatibility;
   - if it is not yet justified, retain the canonical reference representation and defer binary encoding.

9. **R41-8 — Release truth audit and distillation**
   - skeptical cross-host audit;
   - documentation synchronization;
   - release example(s);
   - explicit accounting of unsupported Core IR/capabilities and deferred work.

### Required invariants

- Core IR remains the portability boundary; R41 does not create a parallel IR.
- A runtime host does not need a Genia source compiler to execute a supported artifact.
- Artifact loading is a validation/trust boundary, not deserialization followed by best-effort execution.
- Capability requirements are explicit and checked before execution where possible.
- Artifact format compatibility and Genia semantic compatibility are versioned independently.
- Host-local optimization remains downstream of validated portable Core IR and cannot change semantics.
- Unknown or unsupported artifact features fail deterministically rather than silently degrading.
- Resource limits for decoding/validation must be explicit enough to reject hostile or pathological artifacts safely.

### Dependencies and scheduling

R41 depends on the completed R16 multi-host portability/conformance foundation and on a sufficiently conforming second host to make cross-host artifact evidence meaningful. It should not interrupt R24's minimal C++ host bootstrap merely to invent a file format from the Python implementation.

R41 does **not** depend on R35–R38. It may be scheduled once the C++ host can consume enough shared Core IR to prove the artifact boundary. If R24 exposes ambiguity in Core IR itself, that ambiguity must be resolved in the authoritative Genia contracts before R41 freezes artifact compatibility around it.

### Explicit non-goals

- a browser host implementation;
- a browser compiler;
- JIT compilation or host optimization policy;
- a new semantic IR;
- arbitrary host-language object serialization;
- embedding ambient credentials or secret payloads in artifacts;
- packaging external native dependencies;
- remote code distribution, registries, signing infrastructure, or deployment orchestration;
- freezing a compact binary encoding before the logical model and cross-host evidence are stable.

### Success criterion

A supported Genia program can be compiled once into a versioned portable artifact, then the same artifact can be validated and executed by the Python and C++ hosts with conformant normalized results, while neither artifact-execution path needs to lex, parse, or lower the original Genia source.

The resulting contract must make it architecturally credible for a later browser host to begin as an artifact-only interpreter rather than a browser-resident Genia compiler.
