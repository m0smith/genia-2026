## Release R39 — Genia-Native Conformance Tooling

**Status: Planned, not active.** R39 depends on R18, R35, and R36. It migrates shared-spec orchestration into Genia without inventing filesystem, equality, process, or YAML semantics ad hoc.

Theme:

> Run Genia's shared conformance workflow as a Genia program while keeping storage/process mechanics behind previously approved portable boundaries.

Core planned decisions retained from former R33:

- freeze parity baseline against the Python runner/shared-spec corpus first
- implement a Genia-native YAML parser for the explicitly contracted Genia Spec YAML profile, not hand-wave YAML through host libraries
- scanner -> YAML node tree -> resolver -> ordinary Genia values architecture
- deterministic source positions/diagnostics and explicit unsupported-feature handling
- dual-loader structural parity under R18 before Genia YAML becomes authoritative for this workflow
- migrate spec-envelope validation, capability filtering, comparison/normalization, aggregation, reporting, and deterministic evidence
- discover/read specs through R35 Store/Location/ResourceSnapshot
- invoke host adapters through approved execution boundaries rather than ad hoc
  host-local subprocess APIs: collected `execution.process` is the concrete
  direct-execution need, while R36 remains the broader location-independent
  Genia-execution abstraction
- preserve R16 protocol taxonomy, capability discovery, contract-revision checks, transport separation, applicability, and evidence semantics
- require a dual-run parity gate before the Genia-native runner becomes the normal/default workflow: the Python reference runner and Genia-native runner must consume the same shared-spec corpus and agree on spec discovery/applicability, capability filtering, outcome classification, normalized comparisons, aggregate counts, and deterministic evidence output
- retain a deliberately small Python bootstrap/reference runner as an independent conformance oracle even after the Genia-native runner becomes primary; later cleanup may shrink Python infrastructure, but R39 must not make the implementation under test its only referee
- use the migration as an explicit killer-workflow proving case: shared specs are parsed as messy external records, validated and filtered by capability, executed through the approved host boundary, classified with Outcome-aware logic, aggregated, and rendered as deterministic evidence using Genia's ordinary pipeline abstractions

### Scope clarification: policy versus host mechanics (planning only)

R39 moves portable *policy* over structured data into Genia; it does not move host mechanics. This clarifies existing scope and adds no new release. See `docs/analysis/python-to-genia-meaningful-migration-review.md` (non-authoritative) for the evidence.

- **Host parity gate and known-gap policy are in R39 scope.** `tools/spec_runner/host_parity_gate.py` consumes structured E16-7 evidence and `spec/known_host_gaps.json`, classifies per-capability parity (`PARITY_OK`/`KNOWN_GAP`/`UNDOCUMENTED_GAP`/`STALE_GAP`), applies the failing-count policy, and builds a deterministic report. It is the recommended *first* policy slice (within E39-1/E39-7 ordering below) because it is pure and already has a fabricated-evidence corpus to dual-run against. The Python gate stays authoritative in CI until dual-run agreement, and stays afterwards as part of the independent oracle.
- **Policy is pure over ordinary Genia values.** Envelope validation, capability applicability, comparison, classification, aggregation, evidence/report construction, and parity policy take decoded values as input. Filesystem reads (R35), YAML bytes, process launch/timeout/kill (`execution.process`/R36), clocks, and Git revision lookup remain host-side; the host supplies revision facts as injected values rather than Genia re-implementing Git queries.
- **Shadow before cutover.** Because those slices are pure, their pre-flight may author and test them as non-authoritative shadow modules before the R35/R36 edges exist, provided inputs arrive as ordinary values and no ambient filesystem/process API is added. Authoritative or default use still waits on R35, R36, and the dual-run gate.
- **Canonical evidence bytes are a pre-flight decision.** The Python runner's `encode_evidence()` writes `json.dumps(sort_keys=True, indent=2)` and itself appends the trailing newline; Python's default `json.dumps` escapes non-ASCII, while Genia's `json_encode` does not necessarily use the same byte representation. Define the canonical byte form (or compare parsed values and specify bytes separately) before "byte-identical evidence" becomes a gate.
- **Dual-run corpus includes negative fixtures.** Both runners must agree on non-pass classifications (invalid envelope, unsupported capability, failing comparison, malformed host response), not only on passing cases, so the Genia runner is not refereed only by itself.
- **Not in R39:** replacing the E16-1 subprocess supervision, the Python adapter, PyYAML/Ruby loading in the oracle, Git revision lookup, or GitHub Actions. A Genia-owned release-check program over wider evidence bundles is a parking-lot candidate that R39's parity-gate slice would have to justify.
- A Genia program currently cannot set a process exit status (a returned `err(...)` exits 0); the report-to-exit-status mapping for gate-style programs is a host-edge design question for the R39 pre-flight, not a reason to add an isolated exit API.

Suggested slice order renumbers the former E33 sequence to E39-1 through E39-8 while preserving its intent: baseline and dual-run parity harness; YAML profile parser; envelope validation; R35 discovery/loading; capability filtering; R36 invocation; comparison/evidence/reporting; skeptical parity/truth audit.

Critical acceptance criteria:

- Shared semantic cases can be discovered through R35, parsed by the Genia-native YAML profile parser, invoked through R36, compared under R18, and reported as deterministic evidence by one Genia runner with no Python-specific filesystem/YAML/process logic in its semantic orchestration.
- Before that runner becomes the normal/default workflow, a dual-run gate proves that the Python reference runner and Genia-native runner agree over the same corpus on discovery/applicability, capability filtering, outcome classification, normalized comparisons, aggregate counts, and deterministic evidence.
- The Python reference runner remains available as an independent oracle after cutover; the Genia-native runner becoming primary is not authority to delete the independent implementation.
- Release evidence includes one end-to-end conformance run presented as a killer-workflow proof of Outcome-aware validated data processing rather than as a line-for-line Python port.
