# R39 — Unified Events and Subscriptions

Status: Planned roadmap detail — non-authoritative. `GENIA_STATE.md` remains final authority for implemented behavior.

## Release R39 — Unified Events and Subscriptions

**Status: Planned, not active.** R39 builds on completed R14 lifecycle semantics and the existing Flow abstraction. Its local portable baseline does not require R35/R36, but later resource-watch and distributed-provider realizations must reuse those boundaries where applicable rather than inventing transport-specific application semantics.

Theme:

> Give state changes, Flow/lifecycle instrumentation, resource watches, execution monitoring, future actors, and observability one explicit event/subscription spine without turning events into hidden control flow or inventing a second streaming/lifecycle system.

The design survey is `docs/architecture/unified-events-subscriptions.md`.

Core planned direction:

- events are ordinary immutable Genia values;
- Event (semantic fact) remains distinct from Delivery (one consumer/provider receipt carrying progress, acknowledgement, lease/visibility, or replay metadata when needed);
- explicit EventSource values/capabilities, never an ambient global bus;
- subscription is observed as a Flow of events rather than a new EventStream collection type;
- existing Genia pattern/value machinery is preferred for selection over a parallel string-topic DSL;
- subscriptions that acquire resources are owned and released through R14 lifecycle semantics;
- bounded demand/backpressure is part of the contract; no implicit unbounded buffering;
- cancellation and terminal completion/failure are explicit and align with Flow semantics rather than wrapping every event in a second result protocol;
- ordering is source/order-domain scoped, never a universal global-order promise;
- live versus replayable/history-backed behavior is explicit; the portable baseline is live-only unless a later provider contract says otherwise;
- durability, acknowledgement, competing-consumer groups, replay, and broker mechanics are provider capabilities, not implied by `subscribe`;
- Kafka offsets/partitions and SQS receipt handles/visibility/delete semantics belong to delivery/provider semantics rather than the universal Event value;
- provider-managed execution such as SQS→Lambda-style polling/batching is an execution realization, not a different event model, and should reuse R36 concepts when applicable;
- subscriber failure must not silently corrupt the publisher or unrelated subscribers;
- state remains distinct from events, and Flow remains distinct from Event;
- observation/instrumentation must not change the semantic result of the observed operation merely because a subscriber exists;
- import/load remains inert.

Suggested slice sequence:

1. E39-0 contract, including Event-versus-Delivery and acknowledgement/progress semantics
2. E39-1 ordinary event values and local source
3. E39-2 Flow subscription bridge and bounded-demand proof
4. E39-3 lifecycle ownership
5. E39-4 state-change proving case
6. E39-5 Flow/lifecycle instrumentation proving case
7. E39-6 cross-cutting hardening
8. E39-7 provider-readiness proof with Kafka and SQS/SQS→Lambda semantic mappings, without broker/cloud implementation
9. E39-8 documentation/truth audit and distillation

Critical acceptance criterion:

- One Genia program can explicitly subscribe to ordinary event values from at least a local state/change source and consume them through existing Flow composition with bounded demand and deterministic lifecycle cleanup, while adding/removing an observer does not change the source operation's semantic result and no broker/provider-specific concept leaks into portable application code.

Non-goals:

- actor system/mailbox semantics;
- event sourcing;
- durable event log or broker implementation;
- Kafka/SQS adapters or Lambda runtime integration;
- exactly-once claims;
- global total ordering;
- implicit retry;
- distributed consensus;
- replacement of Flow or Outcome;
- second lifecycle mechanism;
- ambient global event bus.
