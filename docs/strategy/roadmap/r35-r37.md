# R35–R37 — Portable Storage, Location-Independent Execution, and Portable Actors

Status: Planned roadmap detail — non-authoritative. `GENIA_STATE.md` remains final authority for implemented behavior.

These are the former R31-R33 releases shifted after the numeric decomposition and explicit R28 MCP release. Their architectural intent is unchanged.

Cross-cutting capability taxonomy and external direct-process architecture are
recorded in `docs/architecture/host-capability-taxonomy.md` and
`docs/architecture/external-process-execution.md`. They do not assign a new
release number. `execution.process` is now **implemented** in the Python
reference host (`GENIA_STATE.md` section 9.40) — this does not start or
implement any part of R35, R36, or R37 below, all of which remain planned,
not active. R35 may inform process working-location semantics; optional
`execution.process` is distinct from R36 but may become a local provider
mechanism beneath it; R37 is a concrete future dogfooding consumer, now with
an already-implemented primitive to consume once R37 itself begins. Numbered
scheduling requires separate approval.

## Release R35 — Portable Storage and Resource Semantics

**Status: Planned, not active.** R35 defines the portable resource/storage boundary needed by Genia-native tooling and by provider-independent data pipelines. Location/Store/Revision equality behavior consumes R18 rather than creating storage-local equality.

Theme:

> Keep resource identity, storage authority, and provider mechanics separate so the same Genia program can consume local, memory, and cloud-backed resources through one portable contract.

Core planned decisions retained from former R31:

- inert Store-relative `Location`, not OS path/full URI semantics
- explicit bounded identity-bearing `Store` authority with no ambient current filesystem/cloud account/default bucket
- optional restricted substores whose authority never exceeds the parent
- opaque Store/resource-bound `Revision`, never a user-parseable ETag/hash/timestamp/sequence
- immutable `ResourceInfo` and `ResourceSnapshot`
- whole-resource byte reads, metadata, lazy listing, range reads, explicit replace/create-if-absent/revision-conditional mutation/delete where approved
- Outcome distinction between ordinary absence and operational failure
- optimistic concurrency through explicit revision preconditions rather than universal locks/rename assumptions
- provider mechanics/credentials/raw exceptions below the portable boundary
- listing compatible with bounded Seq/Flow consumption
- future streaming content uses the existing Flow abstraction rather than FileStream/S3Stream-specific models
- memory and local Store proving implementations first; cloud providers may follow without changing application Locations/semantics
- R10/R13 protected configuration and R14 lifecycle ownership reused rather than replaced

Critical acceptance criterion:

- One Genia program can enumerate and read provider-neutral resource observations and perform approved revision-aware operations without knowing whether the Store is memory-backed or local-file-backed, while the same contract remains suitable for later object/cloud stores.

## Release R36 — Location-Independent Genia Execution

**Status: Planned, not active.** R36 builds on R14 lifecycle ownership, R16 host protocol/capability/revision lessons, R18 identity/opaque equality, and R35 storage authority where execution needs storage access.

Theme:

> Describe Genia work independently of where it physically executes, then make local execution the first provider rather than the language contract.

Core planned decisions retained from former R32:

- inert portable `Execution` description for bounded Genia computation
- placement/policy separate from execution description
- opaque `ExecutionHandle`, not PID/hostname/container/provider ID
- structured `ExecutionResult` separating returned value, output, diagnostics, and provider metadata
- compatibility negotiation using semantic contract revision/protocol/capability identity
- resource requirements separate from capability/authority requirements
- normalized unsupported/incompatible/unauthorized/launch/timeout/cancel/execution/provider failures
- no implicit retries
- child-execution lifetime integrated with R14
- one local execution provider as the first vertical proof
- provider-specific process mechanics remain below the portable boundary

Critical acceptance criterion:

- One Genia computation can describe and start another bounded computation through a provider-neutral contract and receive the same portable result model without knowing OS process mechanics.

## Release R37 — Portable Actors, Messaging, and Supervision

**Status: Planned, not active.** R37 builds on R14 lifecycle ownership, R16 host protocol/capability/revision lessons, existing Flow semantics, R18 portable identity/equality, and R36 location-independent execution/placement. It defines actor semantics in Genia while keeping execution and transport mechanics behind providers.

Theme:

> Actor semantics belong to Genia. Actor execution and transport belong to providers.

Core planned decisions:

- one portable actor model whose actor definitions and message handling can be written in Genia and run unchanged through different conforming providers
- opaque portable `ActorRef` identity; no PID, thread ID, hostname, ARN, queue URL, container ID, or provider-specific address in application semantics
- explicit portable message/envelope contract covering payload, sender/reply identity where approved, correlation, serialization/version compatibility, ordering guarantees, delivery guarantees, and normalized failure
- mailbox capacity and backpressure are contract concerns rather than accidental host behavior; no provider may silently strengthen or weaken the portable guarantees
- actor lifecycle composes with R14 rather than creating a parallel lifetime model: creation/start/running/stop/termination plus explicitly contracted failure/restart/reactivation behavior
- supervision is explicit and portable: failure observation, parent/child ownership, stop, restart/reactivation policy where approved, escalation, and deterministic cleanup
- placement is separate from actor definition and reuses the R36 provider-neutral placement model; application code must not need `spawn_local_actor`, `spawn_aws_actor`, or equivalent provider-specific actor APIs
- local/pure-Genia execution is the first proving provider; an AWS-oriented provider is a required architectural proving case, but AWS services and identifiers remain below the portable boundary
- an AWS provider may map portable actor requirements onto services such as queues, event routing, compute, and durable state only where the contract permits; the roadmap does not preselect SQS, EventBridge, Lambda, ECS/Fargate, DynamoDB, or another service as language semantics
- actors participate in Flow without collapsing the abstractions: an actor mailbox is not itself a Flow, but lifecycle-owned actor message/event consumption may expose a Flow, and a Flow stage may explicitly send messages to an actor
- actor messaging remains distinct from a future/general cross-cutting publish/subscribe event facility; they may share envelope, transport, lifecycle, backpressure, and provider foundations, but directed actor messaging must not be redefined as broadcast event publication
- actor protocols must be suitable for multi-host conformance evidence under R16 and must normalize provider failures without leaking host exceptions or provider identifiers
- no implicit retry, restart, redelivery, persistence, or durability semantics; each must be explicit in the contract if admitted
- provider authority/configuration consumes R10/R13 and lifecycle ownership consumes R14 rather than inventing actor-specific secret/config/lifetime mechanisms

Required contract/design questions before implementation:

- exact `ActorRef` identity/equality and serialization boundary
- actor definition/behavior shape and state ownership
- message envelope, request/reply/correlation, ordering, delivery, deduplication, and versioning
- mailbox bounds, admission, Flow backpressure interaction, and overload behavior
- lifecycle state machine and the distinction among failure, stop, restart, and reactivation
- supervision tree/relationship semantics and policy surface
- placement/provider selection, capability negotiation, authority, and compatibility checks
- local-provider mapping and at least one AWS-provider mapping proving the same actor program requires no source change
- observability/event hooks that can later compose with a unified publish/subscribe event system without making observability part of actor semantics

Critical acceptance criteria:

- The same Genia actor definition runs through a local Genia provider and an AWS-oriented provider configuration without actor source changes or provider identifiers entering the actor protocol.
- Actor lifecycle, failure, supervision, mailbox/backpressure, and message-delivery observations are represented through one portable contract with shared conformance cases.
- A Flow can explicitly consume actor-produced observations and send values/messages to an actor while preserving Flow bounded-demand and lifecycle cleanup rules.
- No actor behavior is implemented merely by this roadmap entry; R37 still requires contract, design, failing-test, implementation, documentation, audit, and distillation gates.
