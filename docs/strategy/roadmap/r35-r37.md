# R35–R37 — Portable Storage, Location-Independent Execution, and Genia-Native Conformance Tooling

Status: Planned roadmap detail — non-authoritative. `GENIA_STATE.md` remains final authority for implemented behavior.

These are the former R31-R33 releases shifted after the numeric decomposition and explicit R28 MCP release. Their architectural intent is unchanged.

Cross-cutting capability taxonomy and external direct-process architecture are
recorded in `docs/architecture/host-capability-taxonomy.md` and
`docs/architecture/external-process-execution.md`. They do not assign a new
release number. `execution.process` is now **implemented** in the Python
reference host (`GENIA_STATE.md` section 9.40) — this does not start or
implement any part of R35, R36, or R37 below, all of which remain planned,
not active. R35 may inform process working-location semantics; optional
`execution.process` is distinct from R36 but may become a local provider
mechanism beneath it; R37 is a concrete future dogfooding consumer, now with
an already-implemented primitive to consume once R37 itself begins. Numbered
scheduling requires separate approval.

## Release R35 — Portable Storage and Resource Semantics

**Status: Planned, not active.** R35 defines the portable resource/storage boundary needed by Genia-native tooling and by provider-independent data pipelines. Location/Store/Revision equality behavior consumes R18 rather than creating storage-local equality.

Theme:

> Keep resource identity, storage authority, and provider mechanics separate so the same Genia program can consume local, memory, and cloud-backed resources through one portable contract.

Core planned decisions retained from former R31:

- inert Store-relative `Location`, not OS path/full URI semantics
- explicit bounded identity-bearing `Store` authority with no ambient current filesystem/cloud account/default bucket
- optional restricted substores whose authority never exceeds the parent
- opaque Store/resource-bound `Revision`, never a user-parseable ETag/hash/timestamp/sequence
- immutable `ResourceInfo` and `ResourceSnapshot`
- whole-resource byte reads, metadata, lazy listing, range reads, explicit replace/create-if-absent/revision-conditional mutation/delete where approved
- Outcome distinction between ordinary absence and operational failure
- optimistic concurrency through explicit revision preconditions rather than universal locks/rename assumptions
- provider mechanics/credentials/raw exceptions below the portable boundary
- listing compatible with bounded Seq/Flow consumption
- future streaming content uses the existing Flow abstraction rather than FileStream/S3Stream-specific models
- memory and local Store proving implementations first; cloud providers may follow without changing application Locations/semantics
- R10/R13 protected configuration and R14 lifecycle ownership reused rather than replaced

Critical acceptance criterion:

- One Genia program can enumerate and read provider-neutral resource observations and perform approved revision-aware operations without knowing whether the Store is memory-backed or local-file-backed, while the same contract remains suitable for later object/cloud stores.

## Release R36 — Location-Independent Genia Execution

**Status: Planned, not active.** R36 builds on R14 lifecycle ownership, R16 host protocol/capability/revision lessons, R18 identity/opaque equality, and R35 storage authority where execution needs storage access.

Theme:

> Describe Genia work independently of where it physically executes, then make local execution the first provider rather than the language contract.

Core planned decisions retained from former R32:

- inert portable `Execution` description for bounded Genia computation
- placement/policy separate from execution description
- opaque `ExecutionHandle`, not PID/hostname/container/provider ID
- structured `ExecutionResult` separating returned value, output, diagnostics, and provider metadata
- compatibility negotiation using semantic contract revision/protocol/capability identity
- resource requirements separate from capability/authority requirements
- normalized unsupported/incompatible/unauthorized/launch/timeout/cancel/execution/provider failures
- no implicit retries
- child-execution lifetime integrated with R14
- one local execution provider as the first vertical proof
- provider-specific process mechanics remain below the portable boundary

Critical acceptance criterion:

- One Genia computation can describe and start another bounded computation through a provider-neutral contract and receive the same portable result model without knowing OS process mechanics.

## Release R37 — Genia-Native Conformance Tooling

**Status: Planned, not active.** R37 depends on R18, R35, and R36. It migrates shared-spec orchestration into Genia without inventing filesystem, equality, process, or YAML semantics ad hoc.

Theme:

> Run Genia's shared conformance workflow as a Genia program while keeping storage/process mechanics behind previously approved portable boundaries.

Core planned decisions retained from former R33:

- freeze parity baseline against the Python runner/shared-spec corpus first
- implement a Genia-native YAML parser for the explicitly contracted Genia Spec YAML profile, not hand-wave YAML through host libraries
- scanner -> YAML node tree -> resolver -> ordinary Genia values architecture
- deterministic source positions/diagnostics and explicit unsupported-feature handling
- dual-loader structural parity under R18 before Genia YAML becomes authoritative for this workflow
- migrate spec-envelope validation, capability filtering, comparison/normalization, aggregation, reporting, and deterministic evidence
- discover/read specs through R35 Store/Location/ResourceSnapshot
- invoke host adapters through approved execution boundaries rather than ad hoc
  host-local subprocess APIs: collected `execution.process` is the concrete
  direct-execution need, while R36 remains the broader location-independent
  Genia-execution abstraction
- preserve R16 protocol taxonomy, capability discovery, contract-revision checks, transport separation, applicability, and evidence semantics
- retain Python bootstrap/reference infrastructure until independent parity justifies later removal

Suggested slice order renumbers the former E33 sequence to E37-1 through E37-8 while preserving its intent: baseline; YAML profile parser; envelope validation; R35 discovery/loading; capability filtering; R36 invocation; comparison/evidence/reporting; skeptical parity/truth audit.

Critical acceptance criterion:

- Shared semantic cases can be discovered through R35, parsed by the Genia-native YAML profile parser, invoked through R36, compared under R18, and reported as deterministic evidence by one Genia runner with no Python-specific filesystem/YAML/process logic in its semantic orchestration.
