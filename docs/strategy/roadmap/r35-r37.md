# R35–R37 — Portable Storage, Location-Independent Execution, and Unified Events

Status: Planned roadmap detail — non-authoritative. `GENIA_STATE.md` remains final authority for implemented behavior.

R35 and R36 retain the former portable storage/execution architectural intent. R37 is the unified events/subscriptions release promoted during the September 2026 roadmap reconciliation.

Cross-cutting capability taxonomy and external direct-process architecture are
recorded in `docs/architecture/host-capability-taxonomy.md` and
`docs/architecture/external-process-execution.md`. They do not assign a new
release number. `execution.process` is now **implemented** in the Python
reference host (`GENIA_STATE.md` section 9.40) — this does not start or
implement any part of R35, R36, or R37 below, all of which remain planned,
not active. R35 may inform process working-location semantics; optional
`execution.process` is distinct from R36 but may become a local provider
mechanism beneath it. R37's event/subscription baseline remains separate from direct process execution; later execution-monitoring event sources may consume R36/execution foundations where applicable. Numbered scheduling requires separate approval.

## Release R35 — Portable Storage and Resource Semantics

**Status: Planned, not active.** R35 defines the portable resource/storage boundary needed by Genia-native tooling and by provider-independent data pipelines. Location/Store/Revision equality behavior consumes R18 rather than creating storage-local equality.

Theme:

> Keep resource identity, storage authority, and provider mechanics separate so the same Genia program can consume local, memory, and cloud-backed resources through one portable contract.

Core planned decisions retained from former R31:

- inert Store-relative `Location`, not OS path/full URI semantics
- explicit bounded identity-bearing `Store` authority with no ambient current filesystem/cloud account/default bucket
- optional restricted substores whose authority never exceeds the parent
- opaque Store/resource-bound `Revision`, never a user-parseable ETag/hash/timestamp/sequence
- immutable `ResourceInfo` and `ResourceSnapshot`
- whole-resource byte reads, metadata, lazy listing, range reads, explicit replace/create-if-absent/revision-conditional mutation/delete where approved
- Outcome distinction between ordinary absence and operational failure
- optimistic concurrency through explicit revision preconditions rather than universal locks/rename assumptions
- provider mechanics/credentials/raw exceptions below the portable boundary
- listing compatible with bounded Seq/Flow consumption
- future streaming content uses the existing Flow abstraction rather than FileStream/S3Stream-specific models
- memory and local Store proving implementations first; cloud providers may follow without changing application Locations/semantics
- R10/R13 protected configuration and R14 lifecycle ownership reused rather than replaced

Critical acceptance criterion:

- One Genia program can enumerate and read provider-neutral resource observations and perform approved revision-aware operations without knowing whether the Store is memory-backed or local-file-backed, while the same contract remains suitable for later object/cloud stores.

## Release R36 — Location-Independent Genia Execution

**Status: Planned, not active.** R36 builds on R14 lifecycle ownership, R16 host protocol/capability/revision lessons, R18 identity/opaque equality, and R35 storage authority where execution needs storage access.

Theme:

> Describe Genia work independently of where it physically executes, then make local execution the first provider rather than the language contract.

Core planned decisions retained from former R32:

- inert portable `Execution` description for bounded Genia computation
- placement/policy separate from execution description
- opaque `ExecutionHandle`, not PID/hostname/container/provider ID
- structured `ExecutionResult` separating returned value, output, diagnostics, and provider metadata
- compatibility negotiation using semantic contract revision/protocol/capability identity
- resource requirements separate from capability/authority requirements
- normalized unsupported/incompatible/unauthorized/launch/timeout/cancel/execution/provider failures
- no implicit retries
- child-execution lifetime integrated with R14
- one local execution provider as the first vertical proof
- provider-specific process mechanics remain below the portable boundary

Critical acceptance criterion:

- One Genia computation can describe and start another bounded computation through a provider-neutral contract and receive the same portable result model without knowing OS process mechanics.

## Release R37 — Unified Events and Subscriptions

**Status: Planned, not active.** R37 builds on completed R14 lifecycle semantics and the existing Flow abstraction. Its local portable baseline does not require R35/R36, but later resource-watch and distributed-provider realizations must reuse those boundaries where applicable rather than inventing transport-specific application semantics.

Theme:

> Give state changes, Flow/lifecycle instrumentation, resource watches, execution monitoring, future actors, and observability one explicit event/subscription spine without turning events into hidden control flow or inventing a second streaming/lifecycle system.

The design survey is `docs/architecture/unified-events-subscriptions.md`.

Core planned direction:

- events are ordinary immutable Genia values;
- Event (semantic fact) remains distinct from Delivery (one consumer/provider receipt carrying progress, acknowledgement, lease/visibility, or replay metadata when needed);
- explicit EventSource values/capabilities, never an ambient global bus;
- subscription is observed as a Flow of events rather than a new EventStream collection type;
- existing Genia pattern/value machinery is preferred for selection over a parallel string-topic DSL;
- subscriptions that acquire resources are owned and released through R14 lifecycle semantics;
- bounded demand/backpressure is part of the contract; no implicit unbounded buffering;
- cancellation and terminal completion/failure are explicit and align with Flow semantics rather than wrapping every event in a second result protocol;
- ordering is source/order-domain scoped, never a universal global-order promise;
- live versus replayable/history-backed behavior is explicit; the portable baseline is live-only unless a later provider contract says otherwise;
- durability, acknowledgement, competing-consumer groups, replay, and broker mechanics are provider capabilities, not implied by `subscribe`;
- Kafka offsets/partitions and SQS receipt handles/visibility/delete semantics belong to delivery/provider semantics rather than the universal Event value;
- provider-managed execution such as SQS→Lambda-style polling/batching is an execution realization, not a different event model, and should reuse R36 concepts when applicable;
- subscriber failure must not silently corrupt the publisher or unrelated subscribers;
- state remains distinct from events, and Flow remains distinct from Event;
- observation/instrumentation must not change the semantic result of the observed operation merely because a subscriber exists;
- import/load remains inert.

Suggested slice sequence:

1. E37-0 contract, including Event-versus-Delivery and acknowledgement/progress semantics
2. E37-1 ordinary event values and local source
3. E37-2 Flow subscription bridge and bounded-demand proof
4. E37-3 lifecycle ownership
5. E37-4 state-change proving case
6. E37-5 Flow/lifecycle instrumentation proving case
7. E37-6 cross-cutting hardening
8. E37-7 provider-readiness proof with Kafka and SQS/SQS→Lambda semantic mappings, without broker/cloud implementation
9. E37-8 documentation/truth audit and distillation

Critical acceptance criterion:

- One Genia program can explicitly subscribe to ordinary event values from at least a local state/change source and consume them through existing Flow composition with bounded demand and deterministic lifecycle cleanup, while adding/removing an observer does not change the source operation's semantic result and no broker/provider-specific concept leaks into portable application code.

Non-goals:

- actor system/mailbox semantics;
- event sourcing;
- durable event log or broker implementation;
- Kafka/SQS adapters or Lambda runtime integration;
- exactly-once claims;
- global total ordering;
- implicit retry;
- distributed consensus;
- replacement of Flow or Outcome;
- second lifecycle mechanism;
- ambient global event bus.
