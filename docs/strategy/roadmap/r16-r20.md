# R16–R20 — Portability Infrastructure, Open Functions, and Minimal C++ Host

Status: Planned roadmap detail — non-authoritative. `GENIA_STATE.md` remains final authority for implemented behavior.

See also [`multi-host-conformance-policy.md`](multi-host-conformance-policy.md) for the repository boundary and synchronization rules shared by R16 and later host releases.

## Release R16 — Multi-Host Conformance Infrastructure

**Status: Complete — E16-0 through E16-8 delivered and audited.** Epic #756 is
closed. #757 / E16-0 approved the contract and current-state inventory; #758 /
E16-1 through #764 / E16-7 delivered the versioned protocol, generic external-host
runner path, capability-aware selection, contract-revision identity, Python
reference-host subprocess parity, external-host repository boundary, and
deterministic conformance evidence. #765 / E16-8 published `docs/releases/R16.md`,
synchronized implemented truth, and recorded a skeptical audit **PASS**. R16
changes conformance infrastructure and host-repository architecture, not Genia
language or Core IR behavior.

Theme:

> Give independently versioned host repositories one honest, repeatable way to prove conformance against the authoritative Genia contract.

Before R16, the shared runner called the Python reference-host adapter directly
and in process, so a second host required a one-off shim. R16 replaced that
single-host assumption with a generic, versioned subprocess adapter protocol
while retaining Python as the semantic reference host and `genia-2026` as the
authoritative contract/spec/conformance repository. The generic path is now
`python -m tools.spec_runner --host '<command>'`; Python remains the only
implemented production host, and `m0smith/genia-cpp` is only a non-semantic
bootstrap shell until R20.

Delivered scope:

- one versioned host-adapter protocol covering the existing `parse`, `lower`/`ir`, `eval`, and `cli` operations
- a machine-readable request/response envelope with normalized result fields and strict separation between protocol output and evaluated-program stdout/stderr
- deterministic handling for malformed responses, timeouts, crashes, unsupported operations, and protocol-version mismatch
- explicit per-host capability advertisement and optional per-case capability requirements so unsupported cases remain visible and are never counted as passes
- exact `genia-2026` contract-revision and adapter-protocol identity for external-host evidence
- a distinction between pinned conformance and current-`main` compatibility/drift
- host-neutral `tools/spec_runner --host` execution with no C++-specific semantic knowledge
- the Python reference host routed through the same subprocess protocol as a proving implementation, with the in-process path retained only as a developer optimization
- an external-host repository contract in which external hosts consume but never redefine Genia semantic truth, Core IR, shared specs, or protocol definitions
- `m0smith/genia-cpp` bootstrapped as the first external production-host repository without a real C++ interpreter, and `hosts/cpp/` transitioned to a pointer
- deterministic per-host/category evidence including contract revision, protocol version, capabilities, applicable-case counts, and pass/fail/unsupported/protocol-error/crash/timeout outcomes
- external-host CI guidance separating pinned conformance from non-blocking current-main drift checks

Critical acceptance criterion — **met**:

- A host located in a separate repository can execute selected capability-compatible shared cases through the generic protocol without the runner containing host-specific implementation knowledge or the host consulting the Python implementation, with deterministic pass, fail, unsupported, crash, timeout, and protocol-error reporting. The R16 release audit proves this against the external `m0smith/genia-cpp` bootstrap placeholder and proves semantic parity for applicable cases through the Python subprocess adapter.

Explicit non-goals preserved:

- no second production interpreter/runtime
- no real C++ host implementation
- no Core IR or language-semantics changes
- no unsupported/unexecuted case treated as passing
- no expansion of current spec-category meaning merely to build the runner
- no requirement that every host support identical capability sets

## Release R17 — Numeric and Ordered-Map Portability Contract

**Status: Planned contract hardening, not active.** R17 may proceed in parallel
with R18 after its own contract approval. R20 depends on both.

Theme:

> Replace Python implementation assumptions with explicit numeric and ordered-map semantics.

Candidate scope:

- decide and document general Genia integer range and arithmetic-overflow
  behavior outside the separately bounded JSON representation boundary
- preserve current observable Python behavior unless an explicitly approved
  language-contract change says otherwise; a C++ implementation must not narrow
  integers accidentally
- state map order as a portable runtime contract across literal construction,
  `map_put`, replacement, removal, reinsertion, iteration, accessors, and
  display/debug representation where order is observable
- distinguish map order from map equality, matching, and JSON object-name
  sorting so those concepts do not become conflated
- add shared eval/error cases for large-integer arithmetic and boundary behavior
- add shared cases for map insertion, replacement, removal/reinsertion, and the
  existing `map_items`/`map_keys`/`map_values` ordering guarantees
- update `GENIA_STATE.md`, `GENIA_RULES.md`, and affected portability docs only
  when the contract and executable evidence land

Critical acceptance criterion:

- A non-Python host can choose an integer and ordered-map representation from the
  written contract alone and pass the same observable cases without consulting
  Python container or arithmetic behavior or another host's implementation source.

Explicit non-goals:

- changing the R9 JSON safe-integer limit
- selecting a C++ library or container implementation in the language contract
- C++ host implementation

## Release R18 — Unicode, Float, and Diagnostic Portability Contract

**Status: Planned contract hardening, not active.** R18 may proceed in parallel
with R17 after its own contract approval. R20 depends on both.

Theme:

> Specify the byte-exact string, number-display, and diagnostic surfaces shared specs already observe.

Candidate scope:

- define the portable public string model, including Unicode scalar/code-point
  behavior, UTF-8 byte length and boundary checks, code-point iteration and
  slicing, invalid UTF-8 handling, and debug escaping
- define exact float display/debug formatting, including shortest-round-trip
  expectations or another explicitly chosen algorithm, exponent spelling,
  integral-looking floats, negative zero, and non-finite values where supported
- inventory the exact diagnostic text currently asserted by shared eval, error,
  parse, and CLI specs and distinguish exact-text contracts from typed/category
  contracts and substring matches
- centralize stable diagnostic templates only where the inventory justifies one
  language-neutral catalog or generation source; do not require runtime data-file
  loading merely to avoid duplicated implementation constants
- add shared Unicode and float edge cases plus representative diagnostic drift
  guards at the observable boundaries
- update the source-of-truth and portability docs when each clarified contract
  is approved and implemented in the Python reference host

Critical acceptance criterion:

- A non-Python host can reproduce normalized string slicing, display/debug text,
  and contracted diagnostics byte-for-byte from the written contract and shared
  evidence without using Python `str`, `repr`, or another host implementation as
  an undocumented specification.

Explicit non-goals:

- redesigning error categories
- locale-sensitive formatting
- requiring ICU or any specific C++ library
- C++ host implementation

## Release R19 — Open Functions and Extensible Pattern Dispatch

**Status: Planned language-semantics release, not active.** R19 is promoted from
the parking lot and must complete its own contract gate before any syntax or
implementation shape is treated as approved. R20 depends on the portable R19
contract and shared evidence.

Theme:

> Let one named function accumulate pattern-dispatched clauses locally and accept explicit cross-module extensions without making import order or host implementation details part of dispatch semantics.

Motivating local behavior:

```genia
gcd(a, 0) = a
gcd(a, b) = gcd(b, a % b)
```

The contract must also reconcile this repeated-definition form with the existing
single-definition/grouped-clause surface so equivalent clause sets have equivalent
dispatch behavior. Exact syntax remains a contract decision rather than roadmap truth.

Motivating cross-module behavior, with spelling deliberately not locked:

```genia
# common/storage surface
get(MemoryStore(store), key) = memory_get(store, key)

# future database module contribution
extend get(Database(db), key) = db_get(db, key)
```

Candidate scope:

- define when repeated compatible local declarations extend one named function
  group rather than rebind/replace an earlier declaration
- preserve existing pattern-based dispatch and fixed-arity-over-varargs precedence
- define explicit cross-module contribution semantics; merely importing a module
  must not silently overwrite or mutate an unrelated visible function
- make dispatch results independent of unrelated module import order
- define deterministic ambiguity behavior when multiple contributed clauses match
  and no approved specificity rule selects one
- retain declaration/module provenance for each contributed clause for diagnostics,
  `help`/introspection, and later reload/unload design
- define duplicate-clause and incompatible-extension diagnostics deterministically
- preserve lexical/module visibility and privacy boundaries rather than turning an
  open function into process-global mutable state
- preserve inert load/import semantics: defining or importing extension clauses
  performs no lifecycle activation, resource acquisition, network IO, or process IO
- specify the feature host-agnostically at the language/Core-IR boundary and add
  shared parse/IR/eval/error/module-conformance evidence before a second host
  implements it
- review existing `GeniaFunctionGroup` behavior only as reference-host evidence;
  Python implementation details must not define the portable semantics

Critical acceptance criterion:

- Equivalent local grouped and repeated clause declarations dispatch identically;
  two explicitly contributing modules can extend one named function interface
  without silent rebinding; unrelated import order cannot change the selected
  clause; and unresolved multi-match cases fail with one deterministic ambiguity
  result that a non-Python host can reproduce from the written contract and shared
  specs alone.

Explicit non-goals:

- locking the example `extend` spelling before the contract gate
- adding a named protocol/interface/typeclass layer
- dynamic runtime mutation of function groups
- module unloading/reloading semantics beyond preserving enough provenance for a
  later design
- changing lifecycle/import activation semantics
- allowing arbitrary host-specific overload-resolution rules
- implementing the C++ host in this release

## Release R20 — C++ Minimal Conforming Host

**Status: Planned, not active.** R20 is the first C++ implementation release and
depends on R16, R17, R18, and the portable open-function/dispatch contract from
R19.

Theme:

> Bring up the smallest useful C++ host over the frozen portable Core IR boundary in `m0smith/genia-cpp`.

Repository boundary:

- all C++ production implementation introduced by R20 belongs in
  `m0smith/genia-cpp`
- `genia-2026` receives only authoritative contract/spec/runner/documentation
  changes needed to support portable behavior
- the C++ repository must record the exact `genia-2026` contract revision it
  implements and must not copy authoritative semantic documents as divergent
  local truth
- if implementation work discovers ambiguous portable behavior, stop host-side
  guessing, clarify the contract/spec upstream in `genia-2026`, then resume C++

Candidate scope:

- choose and document the C++ build, dependency, test, formatting, and lint
  toolchain in `m0smith/genia-cpp`
- implement the current documented lexer/parser surface and normalized parse
  adapter operation
- lower into only the frozen minimal portable Core IR node and pattern families
  before any host-local optimization
- implement Core IR evaluation for capability-light ordinary values and control
  behavior: literals, collections, Outcomes, operators, pipelines,
  case/pattern matching, lambdas, assignments, function definitions, and the
  approved R19 open-function/dispatch behavior within the declared capability set
- implement integers, ordered maps, Unicode strings, float formatting, and
  diagnostics according to R17/R18 rather than C++ defaults
- implement file mode, `-c` command mode, raw `argv()`, prelude loading/autoload,
  and the currently required `help(name)` surface; resolve any capability-matrix
  classification conflict before claiming minimal-host conformance
- maintain evidence-based C++ capability status in the C++ repository and shared
  registry/matrix metadata only as code and shared evidence land
- pass the R16-declared capability-light parse, IR, eval, error, and CLI case
  subsets through the generic runner; the release must publish exact counts and
  unsupported-case reasons rather than claiming an entire mixed-capability
  category passed

Critical acceptance criterion:

- A Genia program within the declared minimal capability set has the same
  normalized parse/Core-IR shape and observable result under the C++ and Python
  hosts for every applicable shared case, including approved R19 function-group
  dispatch cases, with the C++ claim tied to an exact `genia-2026` contract
  revision.

Explicit non-goals:

- `-p`/pipe mode or REPL
- Flow phase 1
- refs, cells, or processes
- HTTP serving or outbound HTTP
- allowlisted host interop, resource IO, model/embedding fixtures, or provider adapters
- defining Genia semantics from C++ implementation choices
