# R26–R30 — Shaped Data, Relational Workflows, Data Boundaries, Tooling, and Performance

Status: Planned roadmap detail — non-authoritative. `GENIA_STATE.md` remains final authority for implemented behavior.

These releases return the roadmap directly to Genia's first killer workflow after R25's Sheet record-pipeline bridge. They are sequenced to deepen the same value/pattern/pipeline model rather than add parallel dataframe, query, workflow, or effect systems.

## Release R26 — Sheet Shaped Computation

**Status: Planned, not active.** R26 depends on R25's explicit Sheet/record boundary and preserves existing immutable Sheet ownership.

Theme:

> Make columns and other shaped values participate in predictable whole-value computation without turning Sheets into mutable spreadsheets or an implicit Seq source.

Candidate scope:

- define portable shape/rank observations needed for Sheet column computation
- define exact scalar lifting over shaped values
- define shape-conformance rules for shaped-vs-shaped operations, including deterministic mismatch diagnostics
- introduce one explicit column-expression boundary for existing Sheet values; exact public names and call shapes belong to the contract gate
- support whole-column derivation where the resulting row count and column identity are deterministic
- define a minimal elemental/lifted-call rule only where one ordinary scalar callable can be applied independently across a conforming shaped value without hidden mutation or side effects
- preserve `some` / `none` / `err` cell values explicitly rather than coercing or silently dropping them
- keep optimization freedom host-local while making observable shape semantics shared and conformance-tested
- add shared eval/error cases for scalar lifting, conforming columns, non-conforming shapes, Outcome cells, and deterministic column order

Critical acceptance criterion:

- A Sheet column expression can combine scalars and conforming columns with identical observable values, shape, Outcome preservation, and diagnostics across conforming hosts without row-by-row application code or implicit Sheet-to-Seq conversion.

Explicit non-goals:

- broad R-style recycling
- automatic cell coercion or inferred column types
- spreadsheet cell formulas or mutable recalculation state
- joins, grouping, pivoting, sorting, windows, or query planning
- a general tensor/ND-array language
- new purity/effect syntax merely to enable optimization

## Release R27 — Relational Sheet Operations

**Status: Planned, not active.** R27 depends on R25 and may consume R26 shaped-computation semantics where useful, but must keep relational operations distinct from elemental shape operations.

Theme:

> Add the small relational toolkit needed for practical validated-data workflows without creating a second SQL or dataframe language inside Genia.

Candidate scope:

- define deterministic `group_by`-style grouping over one or more explicit Sheet columns
- define grouped summarization through ordinary Genia callables and existing Outcome behavior
- define deterministic ordering/sorting with explicit key and direction semantics
- define explicit key-based joins with approved duplicate-key, unmatched-row, column-collision, and output-order behavior
- consider adjacent-run/control-break processing as a record-pipeline operation only if it cannot be expressed clearly with existing `scan`/`reduce` plus the new grouping boundary
- preserve column identity, column order, protected values, and accumulated validation diagnostics through relational operations
- require explicit schema-changing operations; never silently rename, union, pad, or drop columns
- add shared cases proving deterministic grouping, aggregation, ordering, joins, duplicate handling, and Outcome/protected-value preservation

Critical acceptance criterion:

- A validated Sheet can be grouped, summarized, ordered, and explicitly joined into a deterministic immutable Sheet using the same values, Outcomes, Templates, and pipeline model already used elsewhere in Genia.

Explicit non-goals:

- SQL syntax or a SQL parser
- lazy distributed query execution
- optimizer-visible relational algebra as a new public language model
- pivots, windows, recursive queries, or a full dataframe API in the first release
- implicit null/NA semantics separate from Outcome

## Release R28 — Database Data Boundary

**Status: Planned, not active.** R28 builds on the validated-data-pipeline, configuration/secrets, lifecycle, Flow, Sheet, and relational foundations. Exact provider/database support belongs to the contract/design gate.

Theme:

> Make databases ordinary explicit sources and sinks for Genia data pipelines without introducing an ORM or ambient connection state.

Candidate scope:

- define one explicit parameterized-query operation with no string-interpolation shortcut
- define a result boundary that exposes ordered database records through existing Flow/Seq-compatible machinery or explicit Sheet collection without inventing a database-specific stream abstraction
- define explicit write/execute operations and transaction ownership only to the extent required by a concrete proving workflow
- compose credentials through the existing R10/R13 protected configuration model and resource lifetime through the existing R14 lifecycle model
- normalize provider/driver failures into portable Outcome/error categories without leaking raw host exception text
- define deterministic column-name/order handling, duplicate-name handling, numeric/string/bytes boundaries, and unsupported database values
- keep connection/provider selection explicit and capability-scoped; no ambient default database
- prove one end-to-end workflow from parameterized query through validation/reshape to explicit write/report output

Critical acceptance criterion:

- A Genia program can explicitly acquire a configured database boundary, execute a parameterized query, process ordered records through the existing validated-data pipeline, and finalize resources without ORM semantics, ambient state, credential leakage, or host-driver behavior defining the language contract.

Explicit non-goals:

- ORM models, identity maps, lazy relations, migrations, schema-generation frameworks, or active-record behavior
- database-specific query DSL syntax
- automatic transaction retries
- distributed transactions
- treating a driver library's type/coercion/error behavior as Genia semantics

## Release R29 — Developer Experience and Language Tooling

**Status: Planned, not active.** R29 should build on implemented parser/Core-IR/help/debugger surfaces and must not introduce language semantics merely to improve tooling.

Theme:

> Make ordinary Genia development pleasant enough that the language's semantic simplicity is visible in the editor rather than hidden behind tooling friction.

Candidate scope:

- define and ship one canonical formatter for implemented Genia syntax
- harden editor diagnostics against the same parser/Core-IR/semantic truth used by the runtime
- expand go-to-definition, workspace symbols, references, rename safety, hover/help, and signature information where existing syntax/metadata supports them
- provide deterministic source ranges and diagnostic categories needed by editor tooling without changing runtime meaning
- add a minimal project/bootstrap command only if repeated real workflows justify it
- document the supported editor/tooling contract and keep generated/reference help synchronized with implemented behavior
- add conformance/regression tests proving formatter stability/idempotence and tooling-source-range correctness where practical

Critical acceptance criterion:

- A developer can format, navigate, inspect, and diagnose a normal multi-file Genia project using tooling derived from the authoritative parser/Core IR and documentation surfaces, without the editor maintaining a competing understanding of the language.

Explicit non-goals:

- package manager or registry
- notebook runtime
- browser playground
- speculative static type checker
- editor-only syntax or semantics
- duplicating parser/semantic logic in an independent tooling implementation

## Release R30 — Cross-Host Performance and Optimization Evidence

**Status: Planned, not active.** R30 depends on the R21–R24 C++ host arc and should include R25–R27 data-workflow surfaces where both hosts claim the relevant capabilities.

Theme:

> Measure what the second host actually buys Genia, then optimize only where evidence identifies meaningful cost without changing portable semantics.

Candidate scope:

- define reproducible benchmark workloads for startup, parse/lower, scalar eval, pattern dispatch, Flow pipelines, validated record processing, Sheet reconstruction, shaped column computation, and representative relational operations
- publish Python-vs-C++ measurements with exact host revisions, build modes, machine/runtime metadata, warmup policy, and variance rather than headline-only speed claims
- separate language-semantic cost from host/runtime implementation cost where measurements permit
- identify allocation, copying, dispatch, representation, and boundary hot spots revealed by the benchmark suite
- allow narrowly scoped host-local optimizations only when shared conformance proves no observable semantic change
- add regression thresholds only for stable, repeatable measurements; do not turn noisy microbenchmarks into correctness gates
- feed any discovered semantic ambiguity back through the normal upstream contract/spec process rather than optimizing around undocumented Python behavior

Critical acceptance criterion:

- Genia has a reproducible evidence base showing where Python and C++ differ in cost across real killer-workflow operations, and any landed optimizations preserve the same applicable shared conformance behavior.

Explicit non-goals:

- promising a fixed C++ speedup factor
- benchmark-driven changes to language semantics
- premature JIT/compiler architecture
- vectorization/parallelism promises not justified by approved observable contracts
- treating host-specific benchmark results as portable language guarantees
