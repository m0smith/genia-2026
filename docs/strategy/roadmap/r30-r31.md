# R30–R31 — Location-Independent Execution and Genia-Native Conformance Tooling

Status: Planned roadmap detail — non-authoritative. `GENIA_STATE.md` remains final authority for implemented behavior.

These releases turn external Genia invocation into a portable execution model before the spec runner is migrated to Genia. They are infrastructure/dogfooding work: roadmap placement does not define syntax, implement distributed actors, or make remote execution current behavior.

## Release R30 — Location-Independent Genia Execution

**Status: Planned, not active.** R30 builds on R14 lifecycle ownership and R16 host protocol/capability/revision infrastructure. It defines the portable execution boundary needed before Genia-native tooling may invoke another Genia computation.

Theme:

> Describe Genia work independently of where it physically executes, then make local execution the first provider rather than the language contract.

Candidate scope:

- define one inert portable Execution description for bounded Genia computation; construction performs no launch, process creation, network IO, or scheduler interaction
- keep execution target/code identity separate from invocation arguments and input values; first-pass remote portability sends portable Genia values and references deployed/addressable Genia code rather than serializing arbitrary captured closures or host state
- define placement as explicit policy/requirements separate from the Execution value; local placement is the first proving case, not a separate semantic API
- define an opaque ExecutionHandle whose language identity is not an OS PID, hostname, container ID, worker ID, or provider-specific identifier
- define an ExecutionResult/Outcome boundary that distinguishes returned Genia value from stdout/stderr and provider metadata without making process transport channels the language abstraction
- define compatibility negotiation using the existing R16 lessons: Genia semantic contract revision, execution-provider protocol/version identity where needed, and required capability declarations must be checked before execution when the provider can determine incompatibility
- define resource requirements (for example CPU/memory/accelerator constraints) separately from capability/authority requirements (for example storage/network/secret access); exact first-release vocabulary belongs to the contract gate
- define normalized portable failure classes sufficient to distinguish unsupported/incompatible/unauthorized/placement or launch failure/timeout/cancelled/execution failure/provider failure without leaking raw host exceptions or transport-specific details
- define first-pass retry semantics as no implicit retry; any future retry policy must be explicit because one requested execution may otherwise produce multiple physical attempts
- integrate child-execution ownership with the existing R14 lifecycle model rather than inventing independent parent/cleanup semantics; exact attached/detached behavior belongs to the contract gate
- implement one local execution provider as the vertical proving consumer; provider-specific fork/exec/subprocess mechanics remain host capability details below the portable boundary
- prove that a Genia program can construct a bounded child Execution, start it locally, pass structured input, observe completion/failure, and receive the same portable result contract without knowing PID/process mechanics
- add shared contract/spec coverage only for approved portable observable semantics; provider internals remain host-local tests

Critical acceptance criterion:

- One Genia computation can describe and start another bounded Genia computation through a provider-neutral Execution contract, using only portable values/identity/compatibility/lifecycle semantics above the host boundary, while the first local provider hides OS-process mechanics completely.

Explicit non-goals:

- distributed actor semantics, mailboxes, selective receive, actor reactivation, links, monitors, or supervision trees
- durable jobs/workflows, scheduler persistence, Temporal-like replay, cron/scheduling, or exactly-once guarantees
- transparent network-failure semantics or pretending local and remote physical failures are identical
- automatic retries, speculative execution, work stealing, or distributed scheduling
- Kubernetes, Nomad, Ray, Dapr, cloud-provider, SSH, or container-specific public APIs
- arbitrary closure/environment shipping, captured refs/files/sockets/secrets, or host-object serialization
- general shell syntax, shell tokenization, pipes/redirection, or exposing `subprocess`/PID semantics as Genia language behavior
- filesystem/storage design; execution may declare storage capabilities but does not define the storage API
- equality semantics for Execution/ExecutionHandle values beyond whatever separately approved equality contract exists

Future relationship to actors/jobs:

- Actors may later use this execution/provider/placement/compatibility foundation for activation, but actor identity, mailbox ordering, request/reply, supervision, and reactivation require their own contract.
- Durable jobs/workflows may later reuse Execution descriptions while adding persistence, retry/deadline/scheduling/history semantics in a separate release.

## Release R31 — Genia-Native Conformance Tooling

**Status: Planned, not active.** R31 depends on R30 for external Genia invocation. It migrates the semantic orchestration of the shared spec runner into Genia so the language eats its own dog food without allowing the migration to invent filesystem, equality, or execution semantics ad hoc.

Theme:

> Run Genia's shared conformance workflow as a Genia program while keeping host/process/storage mechanics behind previously approved portable boundaries.

Candidate scope:

- migrate pure runner logic first: spec-envelope validation, capability selection, requires filtering, comparison/normalization policy, outcome aggregation, reporting, and deterministic evidence construction
- define or consume separately approved equality/comparison semantics rather than embedding runner-specific equality rules in host code
- consume a separately approved portable resource/storage discovery boundary for spec-case discovery/loading; do not make local filesystem globbing or YAML implementation details into universal execution semantics
- consume the R30 Execution contract for invoking the R16 host-adapter entry point; the Genia runner must not call Python `subprocess` semantics directly or know host-specific launch details
- preserve the existing R16 protocol taxonomy, capability discovery, contract revision checking, stdout/stderr transport separation, applicability rules, and deterministic evidence semantics unless a separately approved contract change says otherwise
- keep the same Genia runner program independent of the provider used to execute host adapters
- retain the current Python runner as bootstrap/reference infrastructure until Genia-native parity is proven; remove or reduce it only through an explicit later migration gate
- prove local-provider parity against the current Python reference host before introducing any remote proving provider
- add one deliberately small remote/fixture execution provider proof only after local parity: changing provider/placement configuration must not require changes to the Genia runner program or spec semantics
- keep provider-specific transport tests separate from shared semantic specs; the shared tests assert portable observable conformance behavior
- keep roadmap/state/docs explicit that Genia-native conformance tooling is dogfooding/infrastructure and does not by itself make remote actors or distributed execution generally available

Critical acceptance criterion:

- The authoritative shared semantic cases can be discovered, validated, selected, invoked through the unchanged R16 host protocol, compared, reported, and emitted as deterministic evidence by one Genia runner whose semantic orchestration contains no Python-specific process logic; changing from the local execution provider to the approved remote fixture provider requires no runner-program change.

Explicit non-goals:

- changing shared-spec YAML semantics merely to simplify the migration
- replacing pytest for Python-host parser/evaluator/runtime internals
- introducing runner-specific filesystem, equality, process, retry, or serialization semantics
- requiring a production distributed scheduler or cloud backend
- making arbitrary Genia programs remotely executable before the R30 contract and provider capability say so
- actor/job/workflow semantics
- deleting the Python runner before independent parity/evidence proves the Genia-native path

## Dependency rule

R31 MUST NOT implement its external-invocation stage by adding an ad hoc process/subprocess API. That stage is blocked on the approved R30 Execution contract and local provider.

Likewise, any filesystem/storage discovery or equality behavior needed by R31 must consume separately approved portable contracts rather than allowing the spec runner to define those foundations implicitly.
