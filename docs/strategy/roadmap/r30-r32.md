# R31–R33 — Portable Storage, Location-Independent Execution, and Genia-Native Conformance Tooling

Status: Planned roadmap detail — non-authoritative. `GENIA_STATE.md` remains final authority for implemented behavior.

These releases establish the portable storage/resource boundary and the portable external-execution boundary before the shared spec runner is migrated to Genia. They are infrastructure/dogfooding work: roadmap placement does not define syntax or implemented language behavior.

## Release R31 — Portable Storage and Resource Semantics

**Status: Planned, not active.** R31 defines the portable resource/storage boundary needed by Genia-native tooling and by the killer workflow's transition from local files to provider-backed data sources without rewriting application-level transformation logic. Its Location/Store/Revision equality behavior consumes the separately approved R18 equality contract rather than defining a storage-local notion of equality.

Theme:

> Keep resource identity, storage authority, and provider mechanics separate so the same Genia program can consume local, memory, and cloud-backed resources through one portable contract.

Candidate scope:

- define `Location` as an inert, immutable, canonical Store-relative resource identifier rather than an OS-native path or full URI; construction/composition/comparison performs no IO
- keep provider/account/bucket/container/native-root selection in Store acquisition/configuration rather than embedding it into ordinary application Locations
- define `Store` as an explicit opaque capability-bearing Genia value representing authority over one bounded namespace; no implicit current filesystem, working directory, cloud account, or default bucket is part of the portable contract
- allow Store roots to absorb deployment-specific prefixes so an application Location such as `incoming/2026/data.json` can remain unchanged across local, memory, S3, GCS, Azure, or other approved providers
- integrate Store acquisition with existing R10/R13 configuration/protected-value boundaries and R14 lifecycle ownership where the provider owns resources; import/load and inert configuration construction must not activate storage IO
- define capability inspection as inert and semantic: capabilities describe supported operation classes, not guaranteed authorization/network success; application code depends on capabilities rather than provider-name conditionals
- define optional namespace-restricted substores / authority restriction without IO, with capabilities that never exceed the parent Store
- define one opaque `Revision` concept bound to the observed Store/resource state; it is not a timestamp, hash, sequence number, ETag string, or user-parseable provider token
- define immutable `ResourceInfo` and `ResourceSnapshot` concepts so metadata/revision and materialized bytes describe one consistent successful observation
- define portable whole-resource byte reads, metadata lookup, lazy listing, byte-range reads, unconditional replacement, create-if-absent, revision-conditional replacement, and deletion semantics where approved by the contract gate
- distinguish normal absence/non-match from operational failure through the existing Outcome model; exact `none(...)` versus `err(...)` reason taxonomy belongs to the contract gate
- use revision-based explicit preconditions for portable optimistic concurrency instead of assuming rename, locking, mutable handles, or filesystem transaction semantics
- require capability honesty: a provider/host that cannot uphold a portable guarantee must report the capability unsupported rather than silently weakening semantics
- keep provider-native metadata, credentials, raw exceptions, ETag/generation/version mechanics, absolute host paths, and cloud SDK values below the portable boundary
- define listing as Seq/Flow-oriented and suitable for bounded consumption; listing must not require eager materialization of an entire namespace
- reserve the future streaming-resource architecture as forward-only, single-use `Flow<Bytes>` with non-semantic chunk boundaries, bounded read-ahead, downstream-demand-driven production, and source finalization when demand ends
- do not require streaming storage implementation in the first acceptance slice; whole-resource reads are sufficient for the Genia-native spec-runner discovery/loading proving path
- before any later storage streaming implementation, explicitly settle the generic Flow terminal-failure contract so source IO failures, normal exhaustion, and downstream cancellation compose consistently across storage, process, network, and queue producers
- provide at least memory and local-store proving implementations first; cloud/object-store providers may be added only through separately approved capability slices and must not change application-level storage semantics
- add shared semantic/spec coverage only for approved portable observable behavior; provider-native mechanics remain host-local tests

Critical acceptance criterion:

- One Genia program can receive an explicit Store, enumerate ResourceInfo beneath a Store-relative Location, read materialized ResourceSnapshots, and perform approved revision-aware mutations without knowing whether the Store is memory-backed or local-file-backed; the same portable contract is intentionally suitable for later S3/GCS/Azure providers without rewriting application Locations or transformation logic.

Backpressure / Flow direction:

- Flow remains Genia's single streaming abstraction rather than introducing `FileStream`, `S3Stream`, or mutable file-handle semantics
- a future ResourceRead content source is a forward-only, single-use Flow of immutable byte chunks
- semantic backpressure is pull-driven: downstream demand controls logical production; bounded operators such as `take` stop further Flow production and trigger source finalization
- hosts/providers may use bounded buffering or read-ahead, but must not eagerly materialize an entire resource merely because a streaming read was created
- chunk size and transport packet boundaries are implementation details; conformance is based on concatenated byte content and observable termination/finalization semantics
- push-backed adapters must use bounded buffering or provider flow control rather than defeating Flow backpressure with unbounded host-side accumulation
- storage streaming is deferred until generic terminal Flow failure semantics are separately approved; roadmap placement here records the architectural constraint, not implemented Flow behavior

Explicit non-goals:

- POSIX filesystem compatibility as the universal storage model
- filesystem-global current directory semantics, home expansion, drive-letter semantics, UNC syntax, or provider-specific URI syntax in portable Locations
- real-directory identity as a base abstraction; object-store prefixes and hierarchical namespaces may expose additional capabilities later
- mutable seekable handles, implicit cursor state, append, locks, symlinks, hard links, watchers, POSIX permission models, or a universal atomic-rename guarantee
- provider-specific public APIs for S3/GCS/Azure/local storage
- embedding credentials, account authority, or provider secrets in Locations or inspectable Store descriptions
- automatic retries, transactions, exactly-once guarantees, distributed leases, or hidden conflict recovery
- streaming writes or multipart-upload publication semantics in the first storage contract
- claiming that all Stores expose identical capabilities
- redefining R18 equality semantics locally; Location is structural, Store identity-bearing, and Revision opaque-token behavior must consume the approved shared equality contract

Relationship to the killer workflow:

- R31 directly supports the existing `messy records in -> clear pipelines -> validated shaped output` product direction by making source/sink boundaries explicit and provider-independent while preserving local behavior
- local files and memory Stores are proving cases; later durable/cloud Stores should reuse the same application-level Location/Store/Outcome model rather than adding cloud-specific pipeline dialects

## Release R32 — Location-Independent Genia Execution

**Status: Planned, not active.** R32 builds on R14 lifecycle ownership and R16 host protocol/capability/revision infrastructure. It consumes R18 equality for Execution/ExecutionHandle identity and opaque-token behavior, and defines the portable execution boundary needed before Genia-native tooling may invoke another Genia computation.

Theme:

> Describe Genia work independently of where it physically executes, then make local execution the first provider rather than the language contract.

Candidate scope:

- define one inert portable Execution description for bounded Genia computation; construction performs no launch, process creation, network IO, or scheduler interaction
- keep execution target/code identity separate from invocation arguments and input values; first-pass remote portability sends portable Genia values and references deployed/addressable Genia code rather than serializing arbitrary captured closures or host state
- define placement as explicit policy/requirements separate from the Execution value; local placement is the first proving case, not a separate semantic API
- define an opaque ExecutionHandle whose language identity is not an OS PID, hostname, container ID, worker ID, or provider-specific identifier
- define an ExecutionResult/Outcome boundary that distinguishes returned Genia value from stdout/stderr and provider metadata without making process transport channels the language abstraction
- define compatibility negotiation using the existing R16 lessons: Genia semantic contract revision, execution-provider protocol/version identity where needed, and required capability declarations must be checked before execution when the provider can determine incompatibility
- define resource requirements (for example CPU/memory/accelerator constraints) separately from capability/authority requirements (for example storage/network/secret access); exact first-release vocabulary belongs to the contract gate
- define normalized portable failure classes sufficient to distinguish unsupported/incompatible/unauthorized/placement or launch failure/timeout/cancelled/execution failure/provider failure without leaking raw host exceptions or transport-specific details
- define first-pass retry semantics as no implicit retry; any future retry policy must be explicit because one requested execution may otherwise produce multiple physical attempts
- integrate child-execution ownership with the existing R14 lifecycle model rather than inventing independent parent/cleanup semantics; exact attached/detached behavior belongs to the contract gate
- implement one local execution provider as the vertical proving consumer; provider-specific fork/exec/subprocess mechanics remain host capability details below the portable boundary
- prove that a Genia program can construct a bounded child Execution, start it locally, pass structured input, observe completion/failure, and receive the same portable result contract without knowing PID/process mechanics
- add shared contract/spec coverage only for approved portable observable semantics; provider internals remain host-local tests

Critical acceptance criterion:

- One Genia computation can describe and start another bounded Genia computation through a provider-neutral Execution contract, using only portable values/identity/compatibility/lifecycle semantics above the host boundary, while the first local provider hides OS-process mechanics completely.

Explicit non-goals:

- distributed actor semantics, mailboxes, selective receive, actor reactivation, links, monitors, or supervision trees
- durable jobs/workflows, scheduler persistence, Temporal-like replay, cron/scheduling, or exactly-once guarantees
- transparent network-failure semantics or pretending local and remote physical failures are identical
- automatic retries, speculative execution, work stealing, or distributed scheduling
- Kubernetes, Nomad, Ray, Dapr, cloud-provider, SSH, or container-specific public APIs
- arbitrary closure/environment shipping, captured refs/files/sockets/secrets, or host-object serialization
- general shell syntax, shell tokenization, pipes/redirection, or exposing `subprocess`/PID semantics as Genia language behavior
- redefining filesystem/storage semantics; execution consumes R31 Store/Location/resource boundaries when it needs storage authority
- redefining equality semantics for Execution/ExecutionHandle values; those consume R18

Future relationship to actors/jobs:

- Actors may later use this execution/provider/placement/compatibility foundation for activation, but actor identity, mailbox ordering, request/reply, supervision, and reactivation require their own contract.
- Durable jobs/workflows may later reuse Execution descriptions while adding persistence, retry/deadline/scheduling/history semantics in a separate release.

## Release R33 — Genia-Native Conformance Tooling

**Status: Planned, not active.** R33 depends on R18 for portable equality, R31 for portable storage/resource discovery, and R32 for external Genia invocation. It migrates the semantic orchestration of the shared spec runner into Genia so the language eats its own dog food without allowing the migration to invent filesystem, equality, or execution semantics ad hoc.

Theme:

> Run Genia's shared conformance workflow as a Genia program while keeping host/process/storage mechanics behind previously approved portable boundaries.

Candidate scope:

- migrate pure runner logic first: spec-envelope validation, capability selection, requires filtering, comparison/normalization policy, outcome aggregation, reporting, and deterministic evidence construction
- consume R18 equality/comparison semantics rather than embedding runner-specific equality rules in host code
- consume R31's approved portable Store/Location/resource discovery boundary for spec-case discovery/loading; do not make local filesystem globbing or YAML implementation details into universal execution semantics
- consume the R32 Execution contract for invoking the R16 host-adapter entry point; the Genia runner must not call Python `subprocess` semantics directly or know host-specific launch details
- preserve the existing R16 protocol taxonomy, capability discovery, contract revision checking, stdout/stderr transport separation, applicability rules, and deterministic evidence semantics unless a separately approved contract change says otherwise
- keep the same Genia runner program independent of the provider used to execute host adapters or to host the approved storage namespace
- retain the current Python runner as bootstrap/reference infrastructure until Genia-native parity is proven; remove or reduce it only through an explicit later migration gate
- prove local-provider parity against the current Python reference host before introducing any remote proving provider
- add one deliberately small remote/fixture execution provider proof only after local parity: changing provider/placement configuration must not require changes to the Genia runner program or spec semantics
- keep provider-specific transport/storage tests separate from shared semantic specs; the shared tests assert portable observable conformance behavior
- keep roadmap/state/docs explicit that Genia-native conformance tooling is dogfooding/infrastructure and does not by itself make remote actors or distributed execution generally available

Critical acceptance criterion:

- The authoritative shared semantic cases can be discovered through R31, validated, selected, invoked through the unchanged R16 host protocol via R32, compared under R18, reported, and emitted as deterministic evidence by one Genia runner whose semantic orchestration contains no Python-specific filesystem or process logic; changing approved Store or execution provider configuration requires no runner-program change.

Explicit non-goals:

- changing shared-spec YAML semantics merely to simplify the migration
- replacing pytest for Python-host parser/evaluator/runtime internals
- introducing runner-specific filesystem, equality, process, retry, or serialization semantics
- requiring a production distributed scheduler or cloud backend
- making arbitrary Genia programs remotely executable before the R32 contract and provider capability say so
- actor/job/workflow semantics
- deleting the Python runner before independent parity/evidence proves the Genia-native path

## Dependency rule

R33 MUST NOT implement its storage/discovery stage by adding ad hoc local filesystem helpers; that stage is blocked on the approved R31 Store/Location/resource contract.

R33 MUST NOT implement its external-invocation stage by adding an ad hoc process/subprocess API; that stage is blocked on the approved R32 Execution contract and local provider.

Likewise, equality/comparison behavior needed by R33 MUST consume the approved R18 portable equality contract rather than allowing the spec runner to define that foundation implicitly.
