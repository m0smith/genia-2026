# R30–R34 — Shaped Data, Relational Workflows, Data Boundaries, Tooling, and Performance

Status: Planned roadmap detail — non-authoritative. `GENIA_STATE.md` remains final authority for implemented behavior.

These releases retain the former R26–R30 plan, shifted after the insertion of R21–R23 exact numeric work and R28 MCP.

## Release R30 — Sheet Shaped Computation

**Status: Planned, not active.** Depends on R29's explicit Sheet/record boundary.

Theme: make columns and other shaped values participate in predictable whole-value computation without mutable spreadsheet semantics or implicit Sheet-to-Seq conversion.

Candidate scope retains the prior plan: portable shape/rank observations; scalar lifting; shape-conformance diagnostics; one explicit column-expression boundary; deterministic whole-column derivation; Outcome preservation; shared eval/error evidence.

## Release R31 — Relational Sheet Operations

**Status: Planned, not active.** Depends on R29 and may consume R30 shaped computation.

Theme: add the small relational toolkit needed for practical validated-data workflows without creating SQL syntax or a parallel dataframe/query language.

Candidate scope retains the prior plan: deterministic grouping/summarization, ordering, explicit key-based joins, duplicate/unmatched/collision/output-order rules, Outcome/protected-value preservation, and shared evidence.

## Release R32 — Portable Data Store Boundary

**Status: Planned, not active.** Builds on validated data pipelines, configuration/secrets, lifecycle, Flow, Sheet, and relational foundations.

Theme: make heterogeneous data stores explicit sources and sinks for Genia pipelines without ORM, ambient connection state, SQL-only semantics, or a second application programming model.

R32 is deliberately broader than a relational database boundary. Its contract must be informed by relational/embedded systems (SQLite, JDBC, ODBC), columnar connectivity (ADBC/Arrow), document stores (MongoDB), key/value stores (DynamoDB), and immutable/Datalog systems (Datomic). The planning survey is [`../../architecture/portable-data-store-survey.md`](../../architecture/portable-data-store-survey.md).

Candidate scope: a capability-bearing data-store value; exact stored-value mapping; bounded-demand Flow source/read semantics; the smallest truthful portable write boundary; explicit provider query capabilities with parameterization; Sheet source/sink composition; R14 transaction/lifecycle ownership; change-feed Flow semantics where supported; R10/R13 credentials and protected sinks; normalized provider failures; one SQLite proving provider; one deterministic non-relational offline proving fixture; external JDBC/ODBC/ADBC/native adapter responsibilities; cross-host conformance and skeptical truth audit.

R32 must not define SQL, JDBC, ODBC, mutable tables, or CRUD as universal database semantics. Provider-native query languages remain explicit provider capabilities. R31's relational Sheet work is compositional input, not the storage model. R32 must also review R35's Store/Location architecture during contract work so the two releases do not create competing generic `Store` abstractions or duplicate authority/lifecycle mechanisms.

Planned slices are E32-0 architecture/contract, E32-1 data-store value/capabilities, E32-2 value mapping, E32-3 incremental source/read, E32-4 write/mutation, E32-5 query, E32-6 Sheet integration, E32-7 transaction/lifecycle composition, E32-8 change feeds, E32-9 SQLite proving provider, E32-10 non-relational proving fixture, E32-11 external adapter boundary, and E32-12 cross-host conformance/truth audit. These names/numbers are planning material until the R32 contract/ticketing gate approves them.

A later separately gated heterogeneous-provider release should prove the audited R32 contract against real materially different stores (at minimum one client/server relational provider, one document or key/value provider, and one change-feed provider) rather than widening R32 indefinitely.

## Release R33 — Developer Experience and Language Tooling

**Status: Planned, not active.**

Theme: make ordinary Genia development pleasant without creating an editor-local language definition.

Candidate scope retains the prior plan: canonical formatter; editor diagnostics; navigation/references/rename/hover/help/signatures; deterministic source ranges; narrowly justified bootstrap tooling; regression evidence.

## Release R34 — Cross-Host Performance and Optimization Evidence

**Status: Planned, not active.** Depends on the R24–R27 C++ host arc and should include R29–R31 data-workflow surfaces where both hosts claim the relevant capabilities.

Theme: measure what the second host actually buys Genia and optimize only where evidence identifies meaningful cost without changing portable semantics.

Candidate scope retains the prior plan: reproducible benchmark workloads; Python-vs-C++ measurements with exact revisions/build/machine metadata; hotspot analysis; narrowly scoped host-local optimizations guarded by shared conformance; stable regression thresholds only where measurements justify them.
