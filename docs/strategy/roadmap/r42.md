# R42 — Persistent Interactive Sessions and Jupyter Kernel

Status: Planned roadmap detail — non-authoritative. `GENIA_STATE.md` remains
final authority for implemented behavior.

## Placement

R42 uses the next unreserved release identifier, but it is intentionally not
scheduled after R41. Release numbers are stable planning identifiers, not a
claim that every lower-numbered release is a dependency. R42 branches from the
completed R26 scripted-REPL foundation and R27's delivered Flow/pipe lane. It
is independent of R28 MCP and should land early enough for R33 developer
tooling, a future browser playground, debugger/shell tooling, and editor
frontends to reuse its interactive-session seam.

This placement avoids reopening R27, renumbering R28's established epic
#700/E28 issue set, or making Jupyter wait for the unrelated R29–R32 data arc.
If R28 and R42 are delivered serially, preserving the already-ticketed R28
work first is reasonable; neither release is a dependency of the other.

## Purpose

Establish the smallest host-neutral persistent interactive-execution contract,
make the existing Python REPL consume it, and use Jupyter as the first new
frontend consumer:

```text
interactive frontend
        |
        v
interactive-session contract
        |
        v
Genia host/runtime
```

The seam owns a session and accepts one complete source submission at a time.
It must define persistent top-level bindings and module/import state,
submission result and output observations, normalized diagnostics, failure
survival, and explicit close/finalization. It must not expose Python `Env`,
`Evaluator`, exceptions, streams, or Jupyter messages as portable contract
types.

The existing R26 portable REPL observations are the behavioral floor. R42
must reuse them rather than create different REPL and notebook evaluation
semantics. The current Python REPL's caller-owned `Env` and `run_source` path
are implementation assets to refactor behind the seam, not the contract
itself.

## Dependencies

Hard dependencies:

- the completed R26 persistent scripted-REPL observations and shared evidence;
- explicit session ownership of a persistent top-level environment, including
  module/import caches;
- deterministic per-submission result, stdout, stderr, and diagnostic
  observations, with failed submissions leaving the session available under
  R26's no-rollback-guarantee rule;
- Python REPL adoption of the shared seam before or with the Jupyter adapter;
- a maintained Jupyter protocol library and offline, credential-free kernel
  tests.

Soft dependencies that may follow the first kernel:

- completion, inspection, hover/help, signatures, and richer source-aware
  diagnostics, coordinated with R33;
- interrupt/cancellation beyond safe host-local kernel shutdown;
- host-neutral rich display values and MIME selection;
- debugger, shell, VS Code/editor, and browser/playground adapters;
- a C++ implementation of the reusable session adapter.

R42 does not depend on MCP, AI providers, Sheet/data-store work, actors/events,
location-independent execution, portable Core IR artifacts, a browser-native
host, or full Python/C++ feature parity.

## Planned gates

### E42-0 — Interactive-session contract

Define host-neutral session lifecycle and one-submission observations, map
them explicitly to the R26 REPL contract, and identify which observations
belong in shared conformance. Acceptance requires an approved contract and
deterministic multi-submission evidence for every observation claimed
portable.

### E42-1 — Python session implementation and REPL adoption

Implement the contract in the Python reference host and route the existing
REPL through it without observable REPL drift. Acceptance requires direct
session tests for persistent bindings, cached imports/modules, result and
stdout/stderr separation, normalized failure recovery, and close behavior,
plus unchanged R26 REPL evidence.

### E42-2 — Minimal Jupyter kernel

Package and register a discoverable **Genia** kernel using a maintained
Jupyter kernel/protocol library. Execute each cell through the E42-1 session.
Acceptance requires offline tests for discovery/installation, successful
execution, canonical result rendering, stdout/stderr, normalized errors,
post-error recovery, cross-cell binding persistence, and shutdown. Import or
kernel discovery must not evaluate Genia source or start a session.

### E42-3 — Cross-mode hardening and release truth

Prove that REPL and Jupyter share the session implementation rather than
duplicating evaluator state; preserve debugger and command/file/pipe behavior;
document the adapter seam available to later frontends; publish one offline
release example; and complete documentation synchronization and a skeptical
release audit.

Issue #1045 is the umbrella for R42. The E42 gates should become separate
implementation issues only when their pre-flight and acceptance criteria are
ready; completion/introspection and rich display should not be speculative
R42 tickets.

## Host-parity boundary

The interactive-session contract must be expressible without Python or
Jupyter types. Portable observations approved by E42-0 belong in shared
conformance. The initial reusable implementation and Jupyter transport are
Python-reference-host work.

C++ is not required to implement Jupyter, nor to expose a new session API, to
retain its completed R26 `repl` capability. A later C++ session adapter may
claim an independently named capability only after passing the applicable
shared session evidence. R42 must not turn Python implementation structure
into C++ semantics or imply full-host parity.

## Explicit non-goals

- new Genia syntax, Core IR, value, evaluation, import, or REPL semantics;
- a second evaluator state owned by the Jupyter adapter;
- handwritten ZeroMQ or Jupyter wire-protocol implementation;
- completion, inspection, refactoring, or language-server scope in the first
  kernel;
- HTML widgets, charts, AI visualization, Flow visualization, or a general
  rich-output registry;
- notebook-file semantics, hidden cell reordering, rollback, saved-session
  restoration, or cross-kernel state sharing;
- MCP coupling, an MCP client, provider credentials, or network-dependent
  basic examples;
- browser runtime implementation, debugger/shell redesign, or mandatory C++
  Jupyter support.

Rich display and interactive ergonomics must be separately contracted after
the minimal kernel supplies evidence for the actual abstraction needed. R33
may consume the R42 session seam for editor-facing completion and inspection;
it must not create an editor-local execution model.
