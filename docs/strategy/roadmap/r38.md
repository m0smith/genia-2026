# R38 — Configuration and Secret Hardening and Ergonomics

Status: Planned roadmap detail — non-authoritative. `GENIA_STATE.md` remains final authority for implemented behavior.

## Release R38 — Configuration and Secret Hardening and Ergonomics

**Status: Planned, not active.** R38 depends only on completed R10 (Configuration & Secrets) and R13 (Configuration Resolution Ergonomics). Its position at the end of the numbered sequence reflects reservation order, not a dependency chain through R14–R37; nothing in R14–R37 blocks it, and it does not block them.

Theme:

> Close the gaps that currently force an application needing a protected outbound credential to bypass the normal `genia` execution path with a host-specific launcher, while giving configuration/secret access the ergonomic surface real applications have started to need.

This release promotes the outstanding candidates from
`docs/parking-lot/post-r13-configuration-followups.md` as one coherent,
still-separately-gated set, rather than letting each wait indefinitely for
its own unscheduled slot. Promotion into this release number does not
approve any candidate's design; each slice below still requires its own
contract, design, failing-tests, implementation, documentation, audit, and
distillation gates, exactly as R10 and R13 required.

Motivating case: the Groq backend of the `ollama_chat` example currently
requires `python -m hosts.python.exec_ollama_chat --backend groq` instead of
`genia examples/ollama_chat.genia --backend groq`, solely because pure Genia
has no approved way to classify a key as secret-only, to mint scoped
declassification authority at the normal execution boundary, or to derive a
protected value from another without fully declassifying it.

Candidate scope, in priority order:

1. **Security-critical (parking-lot Priority 1 — C-9, C-10, C-11):**
   - **C-9** — secret-only provider keys, so `config_get`/`config_view`
     cannot read a key that was only ever meant to be read as a secret.
   - **C-10** — execution-boundary declassification authority, so the
     normal `genia` execution path (file, command, pipe, test, and serve
     modes alike) can construct a provider and mint authority scoped to
     purpose and, ideally, destination, with non-sensitive audit recorded
     by default — removing the need for a host-specific launcher.
   - **C-11** — narrow, explicitly enumerated protected-value
     transformation without declassification: a composition operation
     combining ordinary text with a protected value into a new protected
     value, and a non-revealing fingerprint/identity operation for
     audit/diagnostic correlation. Both compose with existing R9 callable
     Templates for validating the ordinary side, rather than inventing
     parallel validation syntax; neither exposes the protected payload to
     a Template.
   - C-9 has no dependency on C-10 or C-11 and may promote and ship first.
     C-10 is the hardest of the three and needs its own contract before any
     implementation ticket exists. C-11 is independent of both.
2. **Ergonomic (parking-lot Priority 2 — C-1 through C-3):**
   - **C-1** — lifecycle/provider binding — already delivered by R14
     (#694, E14-4); listed here only for completeness of the promoted set.
   - **C-2** — explicit typed/schema-mapped access, reusing R10 conversion
     and callable-Template validation instead of hand-threaded converters
     per key.
   - **C-3** — richer CLI grammar, boolean flags first.
3. **Maturity (parking-lot Priority 3 — C-4):**
   - **C-4** — second-host conformance for the configuration family,
     gated on generic multi-host spec-runner infrastructure that does not
     yet exist. May slip past this release if that infrastructure is not
     ready; it is not required for C-9/C-10/C-11 to ship.

Priority 4 items (C-5 through C-8: `.env` expansion, dot access, structured
config files/remote stores, unknown-option validation) remain explicitly
parked and are not part of R38's candidate scope; each still needs its own
concrete proven demand before promotion, per the parking-lot file's own
promotion trigger.

Non-goals, inherited unchanged from R10/R13 and not reopened by R38:

- new syntax, annotation semantics, or Core IR beyond what C-9/C-10/C-11
  each separately justify and gate;
- memory-erasure guarantees, encryption, key rotation, or external
  secret-manager/vault integration (remains Priority 4 / C-7 territory);
- a second provider implementation, ambient lookup, or implicit
  environment fallback;
- any weakening of R10 protected-carrier, sink, authority, audit, or
  declassification semantics — C-9/C-10/C-11 only add narrowly enumerated
  capability, never loosen an existing rule.

Critical acceptance criterion:

- The `ollama_chat` example's Groq backend runs as
  `genia examples/ollama_chat.genia --backend groq`, with no host-specific
  Python launcher, no discarded audit events, authority scoped to purpose
  and destination, and the stored credential no longer required to already
  carry its HTTP authentication scheme baked into the raw secret text.
