## Release R38 — Portable Actors, Messaging, and Supervision

**Status: Planned, not active.** R38 builds on R14 lifecycle ownership, R16 host protocol/capability/revision lessons, existing Flow semantics, R18 portable identity/equality, and R36 location-independent execution/placement. It defines actor semantics in Genia while keeping execution and transport mechanics behind providers.

Theme:

> Actor semantics belong to Genia. Actor execution and transport belong to providers.

Core planned decisions:

- one portable actor model whose actor definitions and message handling can be written in Genia and run unchanged through different conforming providers
- opaque portable `ActorRef` identity; no PID, thread ID, hostname, ARN, queue URL, container ID, or provider-specific address in application semantics
- explicit portable message/envelope contract covering payload, sender/reply identity where approved, correlation, serialization/version compatibility, ordering guarantees, delivery guarantees, and normalized failure
- mailbox capacity and backpressure are contract concerns rather than accidental host behavior; no provider may silently strengthen or weaken the portable guarantees
- actor lifecycle composes with R14 rather than creating a parallel lifetime model: creation/start/running/stop/termination plus explicitly contracted failure/restart/reactivation behavior
- supervision is explicit and portable: failure observation, parent/child ownership, stop, restart/reactivation policy where approved, escalation, and deterministic cleanup
- placement is separate from actor definition and reuses the R36 provider-neutral placement model; application code must not need `spawn_local_actor`, `spawn_aws_actor`, or equivalent provider-specific actor APIs
- local/pure-Genia execution is the first proving provider; an AWS-oriented provider is a required architectural proving case, but AWS services and identifiers remain below the portable boundary
- an AWS provider may map portable actor requirements onto services such as queues, event routing, compute, and durable state only where the contract permits; the roadmap does not preselect SQS, EventBridge, Lambda, ECS/Fargate, DynamoDB, or another service as language semantics
- actors participate in Flow without collapsing the abstractions: an actor mailbox is not itself a Flow, but lifecycle-owned actor message/event consumption may expose a Flow, and a Flow stage may explicitly send messages to an actor
- actor messaging remains distinct from the R37 cross-cutting publish/subscribe event facility; they may share envelope, transport, lifecycle, backpressure, and provider foundations, but directed actor messaging must not be redefined as broadcast event publication
- actor protocols must be suitable for multi-host conformance evidence under R16 and must normalize provider failures without leaking host exceptions or provider identifiers
- no implicit retry, restart, redelivery, persistence, or durability semantics; each must be explicit in the contract if admitted
- provider authority/configuration consumes R10/R13 and lifecycle ownership consumes R14 rather than inventing actor-specific secret/config/lifetime mechanisms

Required contract/design questions before implementation:

- exact `ActorRef` identity/equality and serialization boundary
- actor definition/behavior shape and state ownership
- message envelope, request/reply/correlation, ordering, delivery, deduplication, and versioning
- mailbox bounds, admission, Flow backpressure interaction, and overload behavior
- lifecycle state machine and the distinction among failure, stop, restart, and reactivation
- supervision tree/relationship semantics and policy surface
- placement/provider selection, capability negotiation, authority, and compatibility checks
- local-provider mapping and at least one AWS-provider mapping proving the same actor program requires no source change
- observability/event hooks that compose with the R37 unified publish/subscribe event system without making observability part of actor semantics

Critical acceptance criteria:

- The same Genia actor definition runs through a local Genia provider and an AWS-oriented provider configuration without actor source changes or provider identifiers entering the actor protocol.
- Actor lifecycle, failure, supervision, mailbox/backpressure, and message-delivery observations are represented through one portable contract with shared conformance cases.
- A Flow can explicitly consume actor-produced observations and send values/messages to an actor while preserving Flow bounded-demand and lifecycle cleanup rules.
- No actor behavior is implemented merely by this roadmap entry; R38 still requires contract, design, failing-test, implementation, documentation, audit, and distillation gates.
