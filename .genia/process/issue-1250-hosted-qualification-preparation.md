## Design / authority boundaries

Artifact JSON and GITHUB_* variables cannot prove hosting. An independent
control-plane operator supplies exact expected repository/workflow revision,
source commit/tree, run/attempt and artifact ID/digest. A read-only GitHub API
client cross-checks repository, immutable commit/tree, workflow bytes at that
revision, successful manual attempt, hosted job/mandatory test step and exactly
one nonexpired artifact. Its server digest must match the downloaded ZIP bytes.
No candidate-supplied artifact URL/path or status flag is a trust root. The
reviewed verifier runs separately from candidate/test processes, never executes
artifact code and never forwards API credentials to storage redirect hosts.

Default provenance policy uses GitHub API run/job/artifact metadata plus its
server SHA-256, not candidate-issued attestations. No OIDC or attestation-write
permission is needed. If policy requires a cryptographically verified attestation,
unsupported/missing verification fails closed; no signature is inferred from JSON.

Extract only bounded ZIPs to a new staging directory: reject absolute/traversal,
backslash/ambiguous/duplicate names, links, special/encrypted/unsupported entries,
unexpected nesting/files, size/ratio bombs and invalid CRC/digest/inventory.
Publish a read-only snapshot only after complete validation; failed extraction
leaves no trusted destination or partial tree. Read-only modes are not a security
boundary against the owner/root; the independent control-plane location is
outside the candidate and not shared writable with any process under test.

A strict receipt binds approved source commit/tree, workflow revision, run/attempt,
artifact ID/digest, manifest and dependency/build digests, scope/expiry and external
review reference. An allowlisted independent GitHub reviewer must APPROVE the
exact source and canonical receipt payload digest through the authoritative API.
Collector/source authors cannot self-issue. Existing same-account COMMENTED
preparation reviews are not silently promoted to machine activation approval.
Receipt stays pending/absent; verification never installs or activates anything.

## Implemented hosted trust model

`hosted_trust.py` requires the independent operator's exact authorization tuple:
repository, workflow numeric ID/path/commit/SHA-256, source commit/tree, run ID,
attempt, artifact ID/name/server SHA-256, manifest, registration proposal,
runtime lock, build evidence/requirements SHA-256 and attestation policy.
All SHAs and numeric identities are strict; branch names cannot substitute.
The authorization file must be outside the candidate checkout. The immutable
reviewed verifier must run on the control plane, never from downloaded code.

Authoritative GET checks bind repository/head-repository IDs and name, both latest
and attempt-specific completed/successful workflow_dispatch records, exact
head SHA, workflow ID/path and workflow file bytes at that SHA, commit tree,
exactly one hosted Ubuntu 24.04 job and successful mandatory test step, then
exactly one nonexpired artifact with matching origin and digest. Reusable
workflows and reruns are unsupported and reject. The server artifact timestamp
must be fresh within 24 hours, with bounded clock skew. API errors, pagination/
artifact ambiguity, missing server digest and insufficient metadata all reject.

Artifact size and downloaded ZIP SHA-256 must match the independently obtained
API fields, not upload-step environment variables. The verifier checks the
contents against current code/test/workflow/policy fingerprints and immutable
inputs, source-identity commit/tree/workflow hash, actual GITHUB repository/run/
attempt/source/workflow SHA claims against the API, exact 42-package target
freezes, identical seven-package backend inventory, non-skipped single-node
JUnit and explicit zero-exit collection outcome. This does not cryptographically
prove CPU execution against a compromised GitHub platform: the trust assumptions
are GitHub's authenticated HTTPS/API, hosted runner service and reviewed pinned
workflow/actions/toolchain/dependencies. New backend behavior remains unaudited.

The default reviewed policy uses GitHub API metadata/server artifact digest.
**No artifact attestation is produced or cryptographically verified here.**
A caller requiring attestations is rejected before retrieval; an unverified
Sigstore/attestation JSON flag cannot enable a fallback. If independent review
requires an attestation-backed policy, a separately reviewed cryptographic
verifier and narrowly scoped OIDC/attestation permissions are a prerequisite,
not an assumed feature of this implementation.

`GitHubReadOnly` only constructs fixed-repository HTTPS GET endpoints, with no
mutation methods. It rejects unexpected redirects. Artifact storage redirects
are restricted to supported Microsoft/GitHub Actions storage domains and use
a new request with **no API Authorization header**; subsequent redirects reject.
Transport errors are redacted rather than retaining signed storage URLs/tokens.
Required external credential: a repository-limited fine-grained token with
Actions read, Contents read and Pull requests read (receipt checks). The operator
must configure read-only scopes; the program cannot introspect all fine-grained
permissions. No credential value is stored in the repository or artifact.

## Manual collection workflow and immutable toolchain

there is no push/PR/workflow_run trigger, activation, registration, acceptance,
PID namespace, signal node, smoke or G0/G1/G2 path. Contents read is its only
explicit repository permission. Checkout credentials are not persisted, and
no GitHub read token is passed to packaging children. Known Actions credential

the runner's dev dependencies. Both frozen subjects get fresh independent caches.

## Retrieval, extraction and independent approval

Future explicitly authorized operator command (not run in this task):

```sh
python -m tools.issue_1250.hosted_trust \
  --authorization /independent-control/authorized-run.json \
  --destination /independent-control/fresh-read-only-evidence \
  --diagnostics /independent-control/fresh-diagnostics
```

Supply GH_TOKEN through the independent credential environment, never JSON or
command text. The operator pins all authorization fields from the reviewed
source plus authoritative run/artifact metadata; they are not copied blindly
from candidate claims. Every diagnostics directory must be fresh: an earlier
verification failure can never be overwritten. Download digest/size, API
identity and failure cause are retained without credentials. No real retrieval
was performed here; test responses are synthetic mocked API fixtures.

`hosted_archive.py` accepts ZIP_STORED/DEFLATED only, maximum 32 MiB archive,
64 MiB expanded total, 8 MiB/member, 256 entries and compression ratio 200.
It rejects absolute/traversal/backslash/drive/ambiguous/duplicate paths, duplicate
manifest keys, Unix links/link extras, special/device/FIFO entries, unsupported
metadata/encryption, unknown paths/nesting, CRC/hash/size/inventory mismatch,
corruption and bombs. Tar/hardlink archives are unsupported and rejected.
Only known evidence files and baseline/candidate paths are allowed. Every file
is read with explicit limits and matched to its declared size and manifest hash.
No extractall or artifact execution occurs.

All checks precede publication. Staging is private and removed on error; files
and directories are sealed read-only before the atomic publication into a new
external destination. Validation failure after publication removes that owned
snapshot. Previous destinations/diagnostics are never overwritten. Permissions
are not protection against root/owner changing modes: use a separate independent
control-plane host/identity and never share this location writable with tests.
The public hosted qualifier requires an in-memory verifier-issued snapshot
capability, not an arbitrary path or deserialized api_verified JSON flag. A
Python private capability is not a sandbox against arbitrary code in the
trusted verifier process; no artifact code is imported/executed there.

`hosted-receipt.pending.json` is an unfilled contract, not active registration.
A future receipt must carry every exact authorization identity/digest plus
APPROVED status, dependency-baseline-activation scope, reviewer, expiry and
PR #1318 review ID. The external reviewer allowlist is independent input.
The canonical payload hash excludes only the review-reference block so a
reviewer can approve it before GitHub assigns the review ID. The authoritative
review must be APPROVED on the exact source commit, authored by an allowlisted
account distinct from collectors/source author, after run completion, and
contain this exact standalone line:

```text
ISSUE1250-APPROVAL sha256:<canonical-receipt-payload-digest>
```

Scope expires no later than 24 hours after run completion. Missing, stale,
self-issued, COMMENTED, mismatched or malformed references reject. The existing
same-account Claude preparation COMMENT reviews cannot satisfy this machine
contract; future independent identity/signature authority must be explicitly
resolved rather than fabricating approval. The receipt is held outside the
candidate. Qualification approval requires a clean local checkout at the exact
approved commit **and tree**; changed source must be staged/reviewed/qualified
again. `require_approved_snapshot` composes content/API proof and receipt checks
but only returns verified data: no caller is connected to active provisioning.
`APPROVED_DEPENDENCIES = None` and old registration remain byte-identical.

The prior activation.proposed.patch and registration proposal are immutable
historical preparation. The old patch is not applied and its bare hosted path
now fails without API proof. It is not an operational activation recipe. A
future independently reviewed final staged implementation must compose the new
trust boundary, isolate credentials from provisioned children and leave the
receipt absent/pending before collecting S. Do not collect before changing
run.py/workflows, then reuse that earlier evidence. Sources now fingerprint all
qualification tooling/tests, both #1250 workflows, policy and pending contract;
actual external receipt data is bound by the independent API approval payload.
