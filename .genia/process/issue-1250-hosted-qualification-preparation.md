## Design / authority boundaries

Artifact JSON and GITHUB_* variables cannot prove hosting. An independent
control-plane operator supplies exact expected repository/workflow revision,
source commit/tree, run/attempt and artifact ID/digest. A read-only GitHub API
client cross-checks repository, immutable commit/tree, workflow bytes at that
revision, successful manual attempt, hosted job/mandatory test step and exactly
one nonexpired artifact. Its server digest must match the downloaded ZIP bytes.
No candidate-supplied artifact URL/path or status flag is a trust root. The
reviewed verifier runs separately from candidate/test processes, never executes
artifact code and never forwards API credentials to storage redirect hosts.

Default provenance policy uses GitHub API run/job/artifact metadata plus its
server SHA-256, not candidate-issued attestations. No OIDC or attestation-write
permission is needed. If policy requires a cryptographically verified attestation,
unsupported/missing verification fails closed; no signature is inferred from JSON.

Extract only bounded ZIPs to a new staging directory: reject absolute/traversal,
backslash/ambiguous/duplicate names, links, special/encrypted/unsupported entries,
unexpected nesting/files, size/ratio bombs and invalid CRC/digest/inventory.
Publish a read-only snapshot only after complete validation; failed extraction
leaves no trusted destination or partial tree. Read-only modes are not a security
boundary against the owner/root; the independent control-plane location is
outside the candidate and not shared writable with any process under test.

A strict receipt binds approved source commit/tree, workflow revision, run/attempt,
artifact ID/digest, manifest and dependency/build digests, scope/expiry and external
review reference. An allowlisted independent GitHub reviewer must APPROVE the
exact source and canonical receipt payload digest through the authoritative API.
Collector/source authors cannot self-issue. Existing same-account COMMENTED
preparation reviews are not silently promoted to machine activation approval.
Receipt stays pending/absent; verification never installs or activates anything.

## Source sequencing

1. Prepare infrastructure (this change); independent Claude infrastructure review.
2. Separately authorize a final staged activation implementation with receipt
   pending/absent, no actual activation. All relevant code/workflows must be final.
3. Independently review staged source S/tree T, then explicitly authorize one
   manual hosted collection at S. New workflow registration on default branch,
   if GitHub requires it, needs separate authorization; none is done here.
4. Collect on S; outside the tested process, verify API run/job/artifact bindings,
   safe extract and exact source/workflow/inputs and mandatory integration.
5. Independent reviewer approves the exact externally held receipt for S/T.
6. Activate only through separately authorized receipt/data selection and later
   exact-SHA acceptance authorization. No executable/workflow changes may reuse
   S's qualification; changing run.py via the old unapplied patch requires a new
   staged review and hosted qualification. No old evidence is grandfathered.

Fingerprints include qualification tooling/tests, workflows and hosted policy.
Receipt is external approval data, not code generated by the candidate. This
phase does not apply the old activation patch or wire an active receipt path.
A later staged implementation is required before the preferred data-only final
activation can be qualified; no claim that today's pre-activation tree qualifies
changed future executables.
